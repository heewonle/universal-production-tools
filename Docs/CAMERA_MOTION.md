# 카메라 모션: 종류만 재현하고 크기는 상수였다 (2026-10-07)

플러그인 효용성을 점검하다 발견한 것이다. 레퍼런스 영상에서 카메라 모션의 **종류**는 정확히
분류하고 있었다(모션 정답 영상 5샷 전부 맞춘다). 그런데 시퀀스를 만들 때 쓰는 **크기**는
코드에 박힌 상수였다.

```cpp
if (Shot.CameraMotion == TEXT("dolly_in")) EndShot.DistanceCm *= 0.65f;
else if (Shot.CameraMotion == TEXT("pan")) { OutRotation.Yaw += 25.0f; return; }
else if (Shot.CameraMotion == TEXT("tilt")) { OutRotation.Pitch -= 18.0f; return; }
```

레퍼런스가 10° 패닝이든 60° 패닝이든 결과는 25°다. **"재현"이라고 부를 수 없는 상태**였고,
생성 결과의 모션 크기를 재는 측정이 하나도 없어 오래 드러나지 않았다.

## 필요한 값은 이미 계산돼 있었다

분석기의 `classify_motion`은 모션을 **가르기 위해** 이런 값들을 만든다.

| 값 | 뜻 |
|---|---|
| `net_tx`, `net_ty` | 배경이 화면에서 움직인 비율(프레임 폭/높이 대비) |
| `net_scale` | 배경 배율 — 줌 |
| `subject_scale` | 인물 크기비 — 돌리(시차로 줌과 구분) |
| `path` | 누적 이동 경로 — 핸드헬드 강도 |

전부 **진단 정보로만 남기고 버리고 있었다.** 이것을 `camera_motion_amount`로 플랜에 실어
시퀀스 빌더가 쓰게 했다.

### 각도로 미리 바꾸지 않는다

플랜에는 **화면 비율로** 남긴다. 레퍼런스 카메라의 화각을 모르기 때문이다. 하지만 목적은
"같은 화면 이동을 만드는 것"이므로 레퍼런스의 화각은 알 필요가 없고, **생성하는** 카메라의
화각으로 역산하면 된다. 그 화각은 우리가 안다.

```
tan α = ScreenDelta · 2 · tan(화각/2)
```

`UPTFraming::ScreenDeltaToRotationDegrees`가 그 계산이다. 시퀀스 빌더와 검증이 같은 함수를 쓴다.

## 정답과 비교해서 두 번 틀렸다

모션 정답 영상은 에디터가 **알려진 크기로** 만든 것이라 추정값을 정답과 직접 비교할 수 있다.

| 샷 | 정답 |
|---|---|
| `MT_02_Pan` | yaw −9° → +9° = **18.0°**, 35mm |
| `MT_03_DollyIn` | 거리 700 → 380cm = 비 **1.842** |
| `MT_04_ZoomIn` | 초점 30 → 55mm = 비 **1.833** |

**1) 화면 이동을 한 번에 각도로 환산했다.** 측정값은 구간별 이동량의 **합**이고 tan은 볼록하므로
Σtan(αᵢ) < tan(Σαᵢ)다. 정답 18° 패닝이 15.96°로 나왔다.
→ 구간 수(`steps`)를 함께 내보내 구간마다 환산해 더한다.

**2) 돌리 거리비에 분류용 값을 썼다.** `half_ratio`는 앞 절반과 뒤 절반의 중앙값 비라 실제로는
샷의 **가운데 절반**만 잰다. 분류에는 그게 더 안전하지만(한 장의 잡음에 안 뒤집힌다) 크기로 쓰면
적게 나온다. 정답 1.842가 1.427로 23% 낮았다.
→ log 크기를 시간에 대해 최소제곱 직선으로 맞춰 0~1 구간으로 외삽한다(`subject_scale_full`).

### 결과

| 항목 | 정답 | 수정 후 | 기존 상수 |
|---|---|---|---|
| 패닝 끝 각도 | 18.0° | **16.4° (−9%)** | 25.0° (+39%) |
| 돌리 끝 거리 | 380cm | **415cm (+9%)** | 455cm (+20%) |
| 줌 끝 초점거리 | 55mm | **49.0mm (−11%)** | 43.5mm (−21%) |

세 항목 모두 오차가 절반으로 줄었다. 남은 ~10% 저추정은 **세 항목에 공통**이라
배경 특징점 추정(ORB + RANSAC 어파인) 쪽으로 보인다. 지금은 수치로 기록해 둔다.

`UniversalProductionTools.CameraMotion.MeasuredAmount` 테스트가 이 수치를 고정한다.
오차 한계와 함께 **"측정값이 기존 상수보다 정답에 가깝다"** 도 검사한다.

## 생성 결과를 되재는 스위트를 만들었다

12개 스위트 중 생성물을 재는 것은 `retarget` 하나뿐이었다. 구도·모션 스위트는 전부
**레퍼런스 영상 분석**을 잰다. 그래서 "종류는 맞는데 크기는 상수"가 통과하고 있었다.

E2E 검증은 샷마다 **시작 프레임 한 장**만 캡처하고 있었다(`모션 샷은 시작 프레임 기준 비교`).
그 한 장으로는 카메라가 얼마나 움직였는지 알 수 없다. → 모션 샷은 **끝 프레임도** 찍는다.
끝 카메라는 시퀀스 빌더가 키를 넣을 때 쓰는 것과 **같은 함수**(`ResolveShotCameraEnd`)로 구한다.
따로 구현하면 검증이 빌더와 다른 것을 재게 되고, 그러면 라운드트립이 아무것도 보장하지 않는다.

### 픽셀로는 못 재는 레벨이 있다

두 프레임에 레퍼런스와 **같은 추정기**를 걸어 봤더니 네 샷 모두 실패했다 —
`L_SlotArena`의 배경에 ORB 특징점이 없다. 정답 촬영 스크립트가 임시 배경 큐브(`UPT_TEMP_BG_*`)를
세우는 이유도 같다.

→ 기하로도 잰다. 시작 카메라 기준으로 정적 월드 점 네 개를 잡고 **생성된 끝 카메라**에 다시
투영해 화면에서 얼마나 밀렸는지 본다. 레퍼런스의 `screen_dx`와 같은 단위가 된다.
두 깊이에서 잰다 — 먼 점은 배경(패닝·줌), 피사체 거리 점은 시차가 섞인 값(돌리)이다.

가는 길에 측정 자체가 한 번 틀렸다. 배율을 "화면 중앙에서 퍼진 정도"로 재니 **순수 회전에서도
배율이 바뀐 것처럼** 나왔다(16° 패닝에서 2.33배). 두 점 **사이 거리**의 비로 바꿨다.

### 결과

| 샷 | 생성 결과 | 레퍼런스 측정값 | 차이 |
|---|---|---|---|
| Pan | dx −0.2915 | −0.278 | **0.0135** |
| Dolly | 인물 배율 1.6875 | 1.688 | **×0.9997** |
| Zoom | 배경 배율 1.633 | 1.633 | **×1.0000** |
| Handheld | dx −0.0373 | +0.020 | 0.0573 (방향 미재현) |

회귀 기준은 네 줄이다.

```
motion_shots                 >= 4
unmeasured                   == 0      기하 측정은 레벨과 무관하게 항상 돼야 한다
dx_error_worst               <= 0.03   현재 0.0135
scale_log_error_worst        <= 0.02   현재 0.0003
```

**이 스위트가 보장하는 것은 정확도가 아니라 사슬의 자기 일관성**이다.
플랜 → 파서 → 솔버 → 시퀀스 빌더를 지나 실제 카메라까지 값이 온전히 전달되는지를 본다.
추정값이 실제 카메라와 얼마나 맞는지는 위의 정답 비교에서 재며, 둘은 다른 주장이고 둘 다 필요하다.

패닝의 0.0135는 구간별 환산의 tan 볼록성 잔차다(−0.278을 16.4°로 바꾼 뒤 다시 화면으로
되돌리면 −0.286이 된다). 핸드헬드는 **폭만 재현하고 방향은 상수**라 위치 오차를 재는 것이
의미가 없어 기준에서 뺀다.

## 재현하지 않는 것

- **틸트 부호가 측정으로 확인되지 않았다.** 모션 정답 영상에 틸트 샷이 없다. 패닝에서
  검증된 같은 모델을 쓰므로 맞을 것으로 보지만, 확인된 것은 아니다. 정답 영상에 틸트 샷을
  추가하는 것이 다음이다.
- **오빗 반경**은 화면 이동만으로 가를 수 없다(측면 이동과 구분되지 않는다). 상수 폭을 유지한다.
- **트럭·페데스탈은 방향을 모션 종류에서 가져온다.** 크기만 측정값으로 바꿨다. 부호 규약
  (`side_cm` 양수가 화면 왼쪽)을 측정으로 확인하기 전에는 방향까지 맡기지 않는다.
- **핸드헬드 방향**은 상수 벡터이고 `path`로 폭만 조절한다.

## 다시 돌리는 법

```bash
# 1) 레퍼런스 영상 분석 (camera_motion_amount가 플랜에 들어간다)
ThirdParty/UPTAnalyzer/.venv/Scripts/python.exe Tools/upt_pose_reference_analyzer.py --video <영상> --output <플랜.json>

# 2) 에디터에서 생성 + 라운드트립 측정
UPT.ReferenceE2E "<플랜.json>" <ActorLabel> -refine=0

# 3) 기준과 비교
python Tools/eval/run_regression.py --only motion_roundtrip
```
