# 스켈레톤 분석기 대규모 검증 (2026-09-28)

자동 리타기팅은 **준비도 70% 미만이면 중단**한다. 이 70%가 실제 자산에서 제대로 작동하는지 확인한 적이 없었다.
프로젝트에 Skeletal Mesh가 1,691개 있으므로, 전부에 분석기를 돌려 등급 분포와 오판을 찾았다.

## 만든 것

콘솔 명령 `UPT.SkeletonAudit [-limit=N] [-filter=문자열] [-out=경로]`
모든 Skeletal Mesh를 로드해 `FUPTSkeletonAnalyzer::AnalyzeDetailed`를 돌리고, 메시별 준비도·등급·역할 매핑·
신뢰도를 JSON으로 남긴다. 1,691개에 21초(메시가 DDC에 캐시된 뒤 기준), 로드 실패 0건.

## 처음 결과

| 등급 | 개수 | 본 수 중앙 |
|---|---|---|
| A (≥90%) | 1,494 | 90 |
| B (≥70%) | 1 | 44 |
| C (<70%) | 196 | 9 |

C등급은 대부분 애초에 휴머노이드가 아니었다 — 2본짜리 `SkeletalCube`, 카메라 리그, 차량·체인 템플릿,
거미·용·개구리 같은 생물. **게이트는 제 역할을 하고 있었다.**

A등급 중 본이 25개 미만인 것은 0개였다. 즉 "너무 작은 리그가 통과한" 경우는 없었다.

## 그런데 통과한 것 중에 틀린 게 있었다

신뢰도 0.6 미만 매핑을 하나라도 가진 메시가 200개(11.8%)였고, 그중 **7개가 A등급으로 게이트를 통과**했다.
대표적인 것이 Mixamo 계열이다.

`X_Bot` (본 65, 준비도 **1.00**, A등급):

| 역할 | 배정된 본 | 신뢰도 | |
|---|---|---|---|
| Root | Hips | 0.57 | Hips는 골반이다 |
| Pelvis | LeftUpLeg | 0.62 | 왼쪽 허벅지다 |
| LeftThigh | LeftLeg | 0.70 | 왼쪽 종아리다 |
| LeftCalf | LeftFoot | 0.70 | 왼쪽 발이다 |
| LeftFoot | LeftToeBase | 0.72 | 왼쪽 발가락이다 |
| RightThigh | RightUpLeg | 0.78 | **이쪽은 맞다** |
| RightCalf | RightLeg | 1.00 | 맞다 |
| RightFoot | RightFoot | 1.00 | 맞다 |

**왼쪽 다리만 한 칸씩 밀렸는데 오른쪽은 정확하고, 그런데도 준비도 100%다.**
팔·머리는 모두 1.00으로 정확해서 평균이 만점이 됐다.

원인은 구조에 있다. 분석기는 **역할을 하나씩 독립적으로** 고르고, 고른 뒤에 역할들 사이의 관계를
확인하지 않는다. 각 역할만 보면 그럴듯하므로 한 칸 밀린 체인이 만점으로 통과한다.

## 고친 것

배정이 끝난 뒤 구조 검사를 한 번 더 돌린다(`UPTSkeletonAnalyzer.cpp`).

1. **부모 역할의 자손인가** — 각 역할의 본이 `ParentRole`의 본 아래에 있어야 한다.
2. **좌우 짝이 같은 깊이인가** — Thigh/Calf/Foot, UpperArm/LowerArm/Hand, Clavicle 쌍은
   대칭 리그에서 같은 깊이여야 한다.

어긋나면 해당 역할의 신뢰도를 0.40으로 깎고, 보고서에 `Structure warnings` 절로 사유를 적는다.
준비도가 함께 떨어지므로 게이트가 막는다.

### 한 번 과하게 잡았다가 되돌린 부분

좌우 깊이 검사를 그대로 넣었더니 Sidekick 계열 10개가 A → B로 내려갔다. 확인해 보니 오탐이었다.

```
foot_l < calf_l < thigh_l < pelvis < root
foot_r < transform2 < calf_r < thigh_r < pelvis < root
```

오른발 위에만 `transform2`라는 중간 본이 하나 더 있는 **비대칭 리그**였고, `foot_l`/`foot_r` 매핑 자체는
이름이 완벽히 일치해 옳았다. 그래서 **양쪽 신뢰도가 0.90 이상이면 깊이 차이를 자산 특성으로 보고 넘긴다**는
예외를 넣었다.

## 추가 (2026-09-29): 이름 근거 없이 배정된 역할을 드러내고, 준비도에서 뺐다

위 "남은 것"에 적어 둔 문제다. 부분 메시(망토·머리 부착물)는 없는 역할을 **남은 아무 본에나** 붙인다.
분석기는 이름 점수 + 위치 점수 + 계층 점수를 더해 0.20을 넘으면 배정하는데,
**이름 점수가 0이어도** 위치·계층만으로 0.20을 넘길 수 있기 때문이다.

실제 예:

| 메시 | 배정 | 신뢰도 |
|---|---|---|
| `SK_Chr_Attach_Cloth_Cloak_01` | `LeftFoot ← jaw` | 0.44 |
| `SK_Chr_Attach_Cloth_Cloak_01` | `RightThigh ← eyes` | 0.20 |
| `SK_VIKG_WARR_03_29ASHL_HU01` | `LeftFoot ← ik_hand_root` | 0.28 |
| `SK_FANT_KNGT_08_24ABAC_HU01` | `LeftHand ← elbowAttach_l` | **0.72** |

마지막 줄이 문제다. **0.72는 '준비됨' 기준(0.55)을 넘는다.** 즉 팔꿈치 부착물 메시가
손 두 개를 팔꿈치 부착 본으로 채워 **준비도 0.75 = B등급**을 받고 있었다.

### 두 가지를 했다

1. **보고서에 표시한다.** 이름 근거가 전혀 없는 배정은 상태를 `GUESS`로 찍고,
   `Forced assignments` 절에 따로 모아 "남은 본 중 위치가 그럴듯한 것을 고른 결과"라고 적는다.
   감사 JSON에도 `forced_roles` 개수와 역할별 `forced` 플래그가 들어간다.
2. **준비도 계산에서 뺀다.** 추측을 '준비됨'으로 세면 등급이 부풀기 때문이다.

### 1,691개에 적용한 결과

| | 변경 전 | 변경 후 |
|---|---|---|
| A | 1,491 | 1,491 |
| B | 1 | **0** |
| C | 199 | **200** |

**등급이 바뀐 것은 정확히 1개**, 위의 `SK_FANT_KNGT_08_24ABAC_HU01`(B 0.75 → C 0.62)이다.
의도한 그 한 개만 움직였고 나머지 1,690개는 그대로다.

강제 배정을 하나라도 가진 메시는 201개이고 그중 196개는 이미 C등급이다.
남은 A등급 4개는 늑대 계열의 `Root ← CG`인데, `CG`(center of gravity)는 실제로 루트 본 이름이라
배정 자체는 맞다. 신뢰도가 0.52로 준비 기준 아래라 등급에도 영향이 없다.
**표시는 하되 막지는 않는** 처리가 여기서는 맞게 동작했다.

### 경계

이 규칙은 "뼈 이름에 아무 단서가 없는 리그"를 전부 C로 내린다. 이름이 완전히 무의미한(예: `joint_01`)
정상 휴머노이드가 있다면 수동 검수로 밀려난다. 자동으로 망가진 결과를 내는 것보다는 낫다고 보고
그대로 두었지만, **이 프로젝트의 1,691개에서 그런 사례가 없었다는 것이지 일반적으로 없다는 뜻은 아니다.**

## 틀린 매핑을 감지만 하지 않고 고쳤다 (2026-10-06)

"남은 것"의 첫 항목이다. 체인 정합성 검사는 **틀린 걸 찾아 막기만 할 뿐 고치지는 못했다.**
Mixamo 계열은 계속 수동 검수로 넘어갔다. 왜 틀리는지부터 다시 봤다.

```
X_Bot (Mixamo)            Polygonal_Golem
  Root    ← Hips            Root    ← RigPelvis
  Pelvis  ← LeftUpLeg       Pelvis  ← RigLLeg1
  LeftThigh ← LeftLeg       LeftThigh ← RigLLeg2
  LeftCalf  ← LeftFoot      LeftCalf  ← RigLLegAnkle
  LeftFoot  ← LeftToeBase   LeftFoot  ← RigLLegFoot1
```

왼쪽 다리가 한 칸씩 밀린 **원인은 다리가 아니라 `Pelvis`였다.**

Mixamo에는 별도의 루트 본이 없고 최상위 본 `Hips`가 곧 펠비스다. `Hips`는 Pelvis 토큰과
**정확히 일치**하는데, 역할을 사양 순서대로 한 번에 배정하다 보니 **Root가 먼저** 집어 간다
(Root는 "부모 없는 본" 가산점 0.50만으로 이름 근거 없이 이긴다). 그러면 Pelvis는 남은 것 중
공간상 그럴듯한 `LeftUpLeg`를 집고, 그 아래가 통째로 밀린다. 골렘도 Root가 `RigPelvis`를
가져가며 똑같이 밀렸다. **이름 근거가 없는 역할이 다른 역할의 정확한 본을 먼저 소비한 것이다.**

### 고친 것

1. **이름 근거가 있는 배정을 먼저 한다.** 두 번에 나눠, 1차는 뼈 이름에 근거가 있는 후보만 보고,
   2차에서 남은 역할을 기존 점수 합으로 배정한다.
2. **루트와 펠비스가 같은 본인 리그를 허용한다.** 1차에서 Pelvis가 최상위 본을 이름으로 가져가면
   Root가 빈손이 되는데, 그건 구조를 잘못 읽은 게 아니라 본이 하나뿐인 것이다. 공유하게 했다.
   (중간에 한 번 덜 고쳤다. "Root가 비었을 때"만 공유하게 했더니 X_Bot은 Root가
   `RightToeBase`를 집은 상태라 발동하지 않았다. "Root에 이름 근거가 없을 때"로 고쳤다.)

|---|---|---|
| A | 1,491 | **1,494** |
| B | 0 | 0 |
| C | 200 | **197** |

**등급이 바뀐 것은 정확히 3개, 전부 개선이다.** 하락 0건.

| 메시 | 전 | 후 |
|---|---|---|
| `X_Bot` (Mixamo) | C 0.44 | **A 0.94** |

X_Bot의 최종 매핑은 **팔다리 전부 신뢰도 1.00**이고 `LeftThigh ← LeftUpLeg`,
`LeftCalf ← LeftLeg`, `LeftFoot ← LeftFoot`으로 좌우가 대칭이다.
매핑이 바뀐 메시는 36개지만 나머지 33개는 전부 C등급 부분 메시로, 바뀐 쪽이 더 맞다
(`LeftThigh ← calf_r` → `thigh_l` 같은 식).

### 실제로 변환되는지까지 확인했다

등급만 올라가고 결과가 나쁘면 의미가 없다. X_Bot을 리타기팅 대상으로 넣어 쟀다.

| 조합 | 뼈마디 각도 중앙 | 최악 |
|---|---|---|
| Synty → UE 마네킹 | 4.7° | 11.5° |
| **Synty → X_Bot (Mixamo)** | **5.2°** | **13.9°** |

**마네킹과 비슷한 수준으로 변환된다.** 이전에는 C등급이라 자동 경로에서 아예 막혀 있던 조합이다.

## 남은 것

- `Pelvis ← Hips` 신뢰도가 0.40에 머문다. 매핑은 맞지만 점수가 낮은데, 공유된 루트 본에
  "자식이 3개 이상" 가산점이 제대로 붙지 않는 듯하다. 등급에는 영향이 없지만 보고서가 혼란스럽다.
- 1·2차 분리는 **사양 순서 안에서만** 작동한다. 같은 차수 안에서 두 역할이 같은 본을 노리면
  여전히 먼저 나온 역할이 가져간다. 전역 최적 배정(헝가리안 등)이 다음 수준이다.

## 다시 돌리는 법

```
UPT.SkeletonAudit -out=<경로>/skeleton_audit.json
```

결과 JSON에는 메시별 `readiness`, `tier`, 역할별 `bone`·`confidence`가 들어 있다(1,691개 기준 약 3MB).
