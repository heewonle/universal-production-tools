# 리타기팅 품질 측정과 자세 정렬 수정 (2026-09-28)

구도 쪽에는 회귀 검사가 11종 있었지만 **애니메이션 리타기팅에는 측정이 하나도 없었다.**
"리타기팅 품질은 어떻게 확인했나"에 답할 수 없는 상태였다. 그래서 먼저 재는 장치를 만들고, 그 결과로 버그를 찾아 고쳤다.

## 무엇을 어떻게 재는가

체형이 다르면 뼈 길이가 달라 관절 **위치**를 그대로 비교할 수 없다. 그래서 두 가지를 본다.

- **뼈마디 방향(segment_angle)** — 관절과 관절을 잇는 방향이 원본과 얼마나 같은가. 체형과 무관하다.
- **발 미끄러짐(foot_slide)** — 발이 땅에 붙어 있어야 할 구간에서 옆으로 흐르는 정도. 다리 길이로 정규화한다.
  리타기팅에서 가장 먼저 깨지는 지점이다. 원본도 완전히 고정되지는 않으므로 **원본 값과 함께** 본다.

만든 것:

| 파일 | 역할 |
|---|---|
| `UPT.RetargetE2E` (콘솔 명령) | 패널 없이 같은 리타기팅 경로 실행, 원본↔결과 쌍을 manifest로 |
| `Tools/eval/editor/upt_capture_retarget_poses.py` | 두 애니메이션을 같은 시각에 24표본 샘플링, 컴포넌트 공간 좌표로 저장 |
| `Tools/eval/eval_retarget.py` | 뼈마디 방향·발 미끄러짐 계산, 회귀 기준 비교 |

애니메이션을 재생하지 않고 `AnimationLibrary.get_bone_pose_for_time`으로 포즈를 직접 읽으므로
시뮬레이트가 필요 없다(부모 기준 로컬 트랜스폼을 계층을 따라 합성한다).

## 처음 측정에서 나온 것

Synty 고블린 애니메이션 → UE 마네킹(SKM_Manny) 리타기팅. 다리 길이 90.6 → 95.8cm.

| 뼈마디 | 각도 차이 |
|---|---|
| lowerarm → hand | **58.3°** |
| upperarm → lowerarm | **52.9°** |
| pelvis → spine_01 | 7.8° |
| calf → foot | 6.5° |
| thigh → calf | 2.2° |

**다리·척추는 잘 맞는데 팔만 53~58° 어긋났다.**

표본별로 보니 각도가 24개 표본 전부에서 **표준편차 0.0으로 완전히 일정**했다.
즉 동작 자체는 정확히 옮겨졌고, **레스트 포즈(A-Pose/T-Pose) 차이가 보정되지 않아 팔이 통째로 틀어진** 것이다.

## 원인

`UPTIKRetargeterBuilder.cpp`가 자세 정렬을 **의도적으로 건너뛰고 있었다.**

```cpp
// UE 5.7 AutoAlignAllBones는 비표준 Rig의 부분 매핑에서 내부 Assertion을 발생시킬 수 있다.
// 체인 리타기팅은 안전하게 생성하고, 자세 보정은 비교 창에서 필요한 체인만 사용자가 적용한다.
```

이유 자체는 타당했다. 다만 그 비용이 얼마인지 아무도 재지 않았고, 결과적으로 **모든 자동 리타기팅 결과의
팔이 53° 틀어진 채로 나오고 있었다.**

## 고친 것

`AutoAlignAllBones`(전체) 대신 **실제로 매핑된 체인의 본만** `AutoAlignBones`로 정렬한다.
파이썬으로 먼저 실험해 어설션이 나지 않는 것을 확인한 뒤 C++로 옮겼다.

중간에 한 번 덜 고쳤다. 체인의 **시작·끝 본만** 정렬했더니 가운데 `lowerarm`이 빠져
`lowerarm→hand`가 31.9°로 남았다. 끝 본에서 시작 본까지 계층을 거슬러 올라가며 체인 전체를 모으도록 고쳤다.

## 결과

|---|---|---|---|
| 뼈마디 각도 중앙 | 7.8° | 7.0° | **3.7°** |
| 최악 뼈마디 | 58.4° | 34.1° | **10.4°** |
| upperarm → lowerarm | 52.9° | 0.1° | **0.1°** |
| lowerarm → hand | 58.3° | 31.9° | **4.7°** |
| thigh → calf | 2.2° | 0.1° | **0.1°** |
| 발 미끄러짐 (원본 0.0995) | 0.1033 | 0.1036 | 0.1049 |

발 미끄러짐은 원본과 거의 같다. 리타기팅이 미끄러짐을 **더 만들지 않았다**는 뜻이다.

## 추가 측정 (2026-09-29): 10.4°의 정체 — 고정 오프셋과 동작 왜곡을 갈라내기

위 표의 "최악 뼈마디 `calf→foot` 10.4°"를 그대로 두면 **동작이 10° 뭉개졌다**고 읽힌다.
그런데 각도 오차에는 성격이 다른 두 가지가 섞여 있다.

- 두 스켈레톤의 **레스트 포즈가 달라 생기는 고정 오프셋** — 시간에 따라 변하지 않는다
- **동작이 실제로 뭉개져 생기는 변동분** — 시간에 따라 흔들린다

24표본의 각도를 프레임별로 펼쳐 보니 갈라졌다.

| 뼈마디 | 중앙값(전체) | 중앙값 주위 흩어짐(표준편차) | 최소~최대 |
|---|---|---|---|
| `pelvis → spine_01` | 7.8° | **0.01°** | 7.7 ~ 7.8 |
| `neck_01 → head` | 8.7° | **0.00°** | 8.7 ~ 8.8 |
| `calf_r → foot_r` | 10.0° | 1.84° | 6.4 ~ 13.1 |
| `calf_l → foot_l` | 9.4° | 2.32° | 5.7 ~ 13.1 |
| `lowerarm → hand` | 4.7° | 0.6° | 3.4 ~ 5.9 |
| `thigh → calf` | 0.1° | 0.00° | 0.1 ~ 0.1 |

`pelvis→spine_01`과 `neck_01→head`는 **흩어짐이 0.0°다.** 동작은 완벽히 옮겨졌고, 두 캐릭터가
그 마디를 원래 다른 각도로 들고 있을 뿐이다. `calf→foot`도 10° 중 약 8.6°가 고정 오프셋이고
실제로 흔들리는 폭은 **1.8°**다.

그래서 지표를 하나 더 넣었다. 중앙값에서의 **중앙절대편차(MAD)** 를 `motion_deviation_worst_deg`로 보고한다.

```
worst_segment_deg          10.4   (고정 오프셋 + 동작 왜곡)
motion_deviation_worst_deg  1.81  (동작 왜곡만)
```

**왜 이게 중요한가.** 고정 오프셋은 체인 정렬로 더 줄일 여지가 있지만, 줄이면 다른 마디가 틀어질 수
있는 상충 관계다(한 본의 회전이 그 본과 자식 사이 방향을 정하므로, 어느 마디를 맞출지 선택해야 한다).
반면 동작 왜곡은 순수한 손실이라 무조건 작아야 한다. **두 값을 한 숫자로 합쳐 두면 어느 쪽이 나빠졌는지
구분할 수 없다.** 실제로 이 분해를 하기 전까지 "최악 10.4°"는 나쁜 값처럼 읽히고 있었다.

회귀 기준에 `motion_deviation_worst_deg <= 3.0`을 추가했다.

### 한 가지 경계

고정 오프셋을 0으로 만드는 방향의 "개선"은 조심해야 한다. 지금 재는 지표가 바로 그 마디의 각도이므로,
그 마디만 맞추도록 정렬 규칙을 바꾸면 **지표에 맞춰 튜닝하는 것**이 된다. 여기서는 오프셋을 줄이는
수정을 하지 않고, 두 값을 갈라 보고하는 데까지만 했다.

## 두 번째 캐릭터 쌍을 넣자마자 에디터가 죽었다 (2026-09-29)

위 "남은 것"의 첫 항목이다. 표본이 **캐릭터 쌍 1개**뿐이라 이 기준이 일반적인지 알 수 없었다.
그래서 체형과 명명 규칙이 모두 다른 쌍을 하나 더 넣었다.

| | 대상 | 본 수 | 명명 | IK Rig 생성 경로 |
|---|---|---|---|---|
| 기존 | `SKM_Manny` | 164 | `thigh_l` | 엔진 Auto Characterizer |
| 추가 | `Forest_Golem_1_PolyArt` | 43 | `L-Thigh` | 자체 분석(폴백) |

먼저 측정 장치부터 고쳐야 했다. 정답 촬영 스크립트가 `thigh_l` 같은 **UE 표준 뼈 이름을 그대로 박아
두고** 있어서 다른 명명 규칙에서는 아무것도 못 읽는다. `UPT.SkeletonAudit`으로 메시마다
**역할 → 뼈 이름**을 받아 오고, 저장하는 JSON의 키도 뼈 이름이 아니라 **역할 이름**으로 바꿨다.
이제 명명 규칙이 달라도 그대로 비교된다.

그리고 골렘을 대상으로 `UPT.RetargetE2E`를 돌리자 **에디터가 통째로 내려갔다.**

```
Assertion failed: ChainToMatch != NAME_None
IKRigEditor/Private/RetargetEditor/IKRetargeterPoseGenerator.cpp:118
"Bone should never be retargeted and not in a mapped chain."
```

**원래 코드의 주석이 경고하던 바로 그 어설션이다.** 자세 정렬을 건너뛰던 이유가 이것이었고,
내가 "매핑된 체인의 본만 고르면 안전하다"고 고쳐 놓은 것은 **Synty→Manny 한 쌍에서만 참**이었다.

### 무엇이 문제였나

엔진 소스를 읽어 보니 `AutoAlignBones`에 함정이 둘 있다.

1. **빈 배열을 넘기면 "전부 정렬"로 해석한다.** `AutoAlignAllBones`와 같아진다.
   매핑 판정을 잘못해 목록이 비면, 안전해지는 게 아니라 가장 위험한 호출이 된다.
2. `AlignBone`은 `IsBoneInAMappedChain`으로 한 번 거르지만, 그 뒤 `GetChainNameForBone`이
   **그 본이 속한 다른(매핑되지 않은) 체인**을 돌려주면 그대로 `checkf`에 걸린다.
   손목처럼 팔 체인의 끝이면서 손가락 체인의 시작이기도 한 본이 여기 해당한다.

매핑 여부를 세 가지 방법으로 판정해 봤고 모두 실패했다.

| 시도 | 결과 |
|---|---|
| `Controller->GetChainMapping()` (인자 없이) | 비어 있는 op의 매핑을 돌려줘 **전부 미매핑**으로 판정 → 정렬이 통째로 꺼지고 Manny가 수정 전 수치(58.4°)로 되돌아감 |
| 원본 Rig에 같은 이름의 체인이 있는지 | Manny가 어설션 |
| op를 훑어 실제 체인 매핑을 읽기 + 다중 소속 본 제외 + 루트/펠비스 제외 | Manny는 통과, **골렘은 여전히 어설션** |

### 그래서 어떻게 했나

정렬을 **엔진 Auto Characterizer가 만든 Rig에서만** 수행하고, 자체 분석(폴백)으로 만든 Rig에서는
건너뛰면서 로그로 알린다.

```
UPT_RETARGET 'Forest_Golem_1_PolyArt' 는 자체 분석으로 만든 IK Rig이라
레스트 포즈 자동 정렬을 건너뜁니다. A-Pose/T-Pose 차이가 남을 수 있습니다.
```

원래 주석이 옳았다. 내 수정이 틀린 게 아니라 **적용 범위를 확인하지 않은 것**이 틀렸다.

### 지금 수치

| 대상 | 뼈마디 각도 중앙 | 최악 뼈마디 | 정렬 |
|---|---|---|---|
| `SKM_Manny` | **3.7°** | 10.4° (`calf_r→foot_r`) | 적용 |
| `Forest_Golem_1_PolyArt` | **18.4°** | 70.0° (`lowerarm_r→hand_r`) | 건너뜀 |
| 동작 왜곡(고정 오프셋 제외) | — | **2.77°** | 두 쌍 공통 |
| 발 미끄러짐 (원본 0.0995) | — | **0.0841** | 두 쌍 공통 |

골렘의 70°는 **레스트 포즈 차이**다. 고정 오프셋을 뺀 동작 왜곡은 2.77°로,
정렬이 적용된 Manny와 큰 차이가 없다. **동작 자체는 옮겨졌고 자세만 틀어져 있다** —
`motion_deviation_worst_deg`를 따로 재지 않았다면 "골렘 리타기팅은 70° 망가진다"로 잘못 읽었을 것이다.

### IK 패스는 처음부터 비어 돌고 있었다 (2026-10-07)

앞 절에서 "IK op을 모두 꺼도 수치가 한 자리도 안 변한다"는 것을 확인하고 넘어갔다.
그 자체가 더 큰 사실이었다. 리타기터 에셋을 열어 op 스택과 설정을 그대로 찍어 봤다.

```
=== RTG_UPT_..._to_SKM_Manny  ops=6
  [2] Retarget IK Goals  enabled=True
      chains_to_retarget: (LeftArm),(RightArm),(RightLeg),(LeftLeg)
=== RTG_UPT_..._to_Forest_Golem_1_PolyArt  ops=6
  [2] Retarget IK Goals  enabled=True
      chains_to_retarget:            ← 비어 있음
```

골렘 쪽은 체인이 아예 없었고, Manny 쪽은 체인이 있는데도 아무 일이 일어나지 않았다.
`IKChainsOp.cpp:290`을 보면 답이 있다 — **체인에 IK Goal이 붙어 있지 않으면 건너뛰고**,
하나도 초기화되지 않으면 op 자체가 `bIsInitialized = false`가 되어 실행되지 않는다.

우리 IK Rig에는 **Goal도 Solver도 없었다.** 엔진 경로는 `AutoGenerateRetargetDefinition`으로
체인만 만들고 끝났고(FBIK 생성은 `AutoGenerateFBIK`라는 별도 호출이다), 폴백 경로의 FBIK 생성
코드는 `#if 0`으로 막혀 있었다. 즉 **지금까지의 품질은 전부 FK와 펠비스 이동에서 나온 것**이고
IK 패스는 한 번도 돈 적이 없다.

### 고치고 나니 더 나빠졌다

Goal을 제대로 만들어 붙였다. 엔진 경로는 `AutoGenerateFBIK`를, 폴백 경로는 손·발 역할 본에
Goal을 만들어 같은 이름의 체인에 묶는 코드를 직접 넣었다(엔진 생성기는 내부에서 Auto Characterize를
다시 돌리므로 폴백 Rig에는 쓸 수 없다). 그리고 세 가지 구성으로 19쌍을 다시 쟀다.

| 지표 | IK 없음(지금) | IK Goal | + Floor Constraint | + 루트 고정 |
|---|---|---|---|---|
| 각도 중앙 / 최악 | **0.1° / 8.4°** | 2.6° / 22.1° | 4.4° / 25.2° | 2.2° / 24.1° |
| 동작 왜곡 | **2.46°** | 6.68° | 6.66° | 4.61° |
| 발 높이 오차 | **0.0120** | 0.0165 | 0.0171 | 0.0231 |
| 발 높이 오차 최악 | **0.0413** | 0.0413 | 0.0946 | 0.0869 |
| 접지 불일치 | **0.0417** | 0.0625 | 0.0625 | 0.0625 |
| 발 미끄러짐 (원본 0.0391) | 0.0427 | **0.0409** | 0.0407 | 0.0470 |

**IK를 쓸 이유는 접지인데, 접지가 나아지지 않았다.** 세 구성 모두 접지 불일치가
0.0417 → 0.0625로 같은 폭만큼 나빠졌고, 발을 바닥에 붙이라고 넣은 Floor Constraint는
오히려 발 높이 오차 최악값을 0.0413 → 0.0946으로 **두 배 넘게** 키웠다.

가는 길에 두 번 걸렸다.

- **Floor Constraint의 부모 op은 `Retarget IK Goals`가 아니라 `Run IK Rig`이다**
  (FloorConstraintOp.cpp:209). 이름만 보고 IK Goals에 붙였더니 정리 단계에서 부모 타입이 맞지
  않아 op이 통째로 사라지고 `Retarget ops were lost during cleaning` ensure로 **에디터가 멈췄다.**
- 엔진 생성기는 Solver 루트를 `Free`로 둔다. 그러면 FBIK가 Goal에 닿으려고 **펠비스까지
  움직여** Pelvis Motion op과 서로를 밀어낸다. `PinToInput`으로 바꾸니 팔은 좋아졌는데
  (`upperarm→lowerarm` 4.0° → 1.0°) 다리가 나빠졌다(`thigh→calf` 3.0° → 5.6°).

### 왜 이렇게 되는가

`Retarget IK Goals`는 Goal 위치를 **원본 체인의 늘어난 정도(정규화 길이)에 대상 체인 길이를
곱해서** 만든다. 우리 FK 경로는 레스트 포즈를 역할 축으로 맞춰 둬서 이미 각도가 거의 정확한데,
IK가 그와 **다른 모델로 계산한 위치**로 팔다리를 끌어당긴다. 각도가 나빠지는 것은 구조상 당연하고,
그 대가로 얻어야 할 접지가 측정에서 나오지 않았다.

→ `UPT.GenerateIKGoals`, `UPT.FloorConstraint`, `UPT.IKPinRoot`는 모두 **기본 끔**이다.
Goal 생성 자체는 이제 제대로 동작하므로, 접지가 각도보다 중요한 다른 에셋에서는 켜고 재면 된다.
지금 19쌍에서는 FK + 펠비스 이동 쪽이 모든 지표에서 낫다.

같이 고친 것: `AcquireIKRig`이 체인만 비우고 Goal과 Solver는 남겨 두고 있었다. 그러면 다시 쓸 때
**새 체인에는 Goal이 붙지 않는데 Solver는 남아 있어**, 겉보기엔 IK가 갖춰진 Rig인데 실제로는
IK가 통째로 건너뛰어지는 상태가 된다. 또 FBIK 생성은 Solver를 무조건 하나 더 넣으므로 돌릴 때마다
Solver가 쌓인다. 셋 다 비우도록 고쳤다.

## 손가락과 트위스트를 처음 재 봤다 (2026-10-12)

19쌍이 전부 몸통 마디만 재고 있었다. 손가락·트위스트는 측정 범위 밖이라, 리타기팅이 그것들을
옮기는지 **아무도 모르는 상태**였다. "범용"을 주장하려면 손이 빠진 채로는 부족하다.

손가락을 분석기의 역할 표에 넣지는 않았다(1,691개 감사의 준비도 계산이 흔들린다). 대신 손
역할 본의 자손을 이름 토큰으로 갈라 `LeftIndex1`·`LeftIndex2` 같은 역할을 붙인다. 이름 규칙이
달라도(`index_01_l` / `L_Index1` / `f_index_01_l`) 토큰은 같으므로 역할과 같은 일을 한다.

트위스트는 위치로는 알 수 없는 본이다 — 팔·다리 축을 따라 **구르기** 때문이다. 그래서
로컬 회전이 샷 동안 움직인 범위를 재고, 그 본이 매달린 역할로 대응시킨다.

### 재 보니 두 자릿수 나빴다

| | 중앙 | 최악 |
|---|---|---|
| 몸통 마디 | 0.1° | 8.4° |
| **손가락 마디** | **15.3°** | **48.8°** |

몸통이 정렬 전에 52.9°였던 것과 **같은 상황**이었다. 역할 그래프에 손가락이 없으니 레스트
포즈 정렬이 손을 건너뛰고, 그 고정 오프셋이 그대로 남은 것이다.

→ 손가락 축을 정렬기에 넣었다. 관절 수가 스켈레톤마다 달라(2개짜리도 3개짜리도 있다) 축을
표에 고정할 수 없으므로, **양쪽에 다 있는 관절만** 이어 붙여 축을 만든다.
정렬 마디가 Manny·X_Bot에서 13개 → **33개**가 됐다(골렘은 손가락이 없어 13개 그대로).

**15.3° → 4.2°.** 그런데 Pinky가 15.2°, Index가 9.6°로 남고 Thumb만 0.0°였다.

### 남은 것은 또 "한 칸 밀림"이었다

UE5 Manny에는 `pinky_metacarpal_l`이 **별도 관절**로 있고 Synty 원본에는 없다. 깊이 순으로
세면 1번 관절이 한쪽은 중수골, 다른 쪽은 기절골이 된다. 중수골이 없는 Thumb만 0.0°였던 것이
그 증거다. 엔진 Characterizer도 중수골을 별도 체인으로 뺀다.

→ 중수골을 관절 번호에서 뺐다(C++ 분석기와 파이썬 캡처가 같은 규칙을 써야 한다).

| 손가락 마디 | 정렬 없음 | 손가락 축 추가 | 중수골 제외 |
|---|---|---|---|
| 중앙 | 15.3° | 4.2° | **0.0°** |
| 최악 | 48.8° | 43.9° | **0.0°** |

열 마디 전부 0.0°다. 포화를 의심해 원본이 실제로 손가락을 움직이는지 확인했다 —
`LeftIndex1→LeftIndex2` 방향이 샷 동안 **원본 69.71°, 결과 69.70°** 변한다.
동작은 처음부터 전달되고 있었고 **고정 오프셋만 남아 있었다**는 뜻이다. 그 오프셋이 사라졌다.

몸통 지표는 한 자리도 변하지 않았다(0.1° / 8.4°, 동작 왜곡 2.46°, 접지 0.012 / 0.0417).

### 트위스트는 통째로 사라졌다 — 재서 판정하고, 고쳤다

```
A_MOD_GBL_Run_F_Neut → SKM_Manny
  LeftUpperArm   원본 13.8°  결과 0.0°
  RightLowerArm  원본 22.8°  결과 0.1°
  LeftThigh      원본  9.1°  결과 0.0°   ... 여덟 역할 전부
```

원본이 4~23° 구르는데 결과는 0.0~0.1°다. 구조상 그렇다 — 트위스트 본은 체인 **경로 밖의
가지**라(`lowerarm_twist_01_l`은 `lowerarm_l`에서 갈라져 `hand_l`로 가는 길에 없다)
FK 체인 리타기팅이 건드리지 않고, 레퍼런스 포즈에 멈춘다.

처음에는 고치지 않았다. UE 관례에서 트위스트는 AnimBP의 보정 노드가 부모 회전으로부터
절차적으로 구동하는 경우가 많아, 구워 넣으면 **두 번 적용**될 수 있기 때문이다.
파이프라인의 의도를 추측해 고치는 것은 이 프로젝트가 피해 온 방식이다.

#### 추측하지 않고 재서 판정했다

"대상 리그에 보정 노드가 있는가"는 AnimBP를 들여다봐야 해서 일반적으로 알 수 없다. 더 직접적인
질문으로 바꿨다 — **그 스켈레톤을 위해 만들어진 애니메이션들이 트위스트를 애니메이션하는가.**
그렇다면 이 파이프라인은 트위스트를 애니메이션에 넣는 쪽이고, 잃는 것은 진짜 손실이다.

| 메시 | 트위스트 본 | 트위스트를 움직이는 원본 애니 | 최대 |
|---|---|---|---|
| SKM_Manny | 26개 | **14/34 (41%)** | 69.4° |
| Retrieve_DefaultWoman | 8개 | **26/40 (65%)** | 81.1° |
| X_Bot / Forest Golem / Wolf | 0개 | — | — |

**표본 크기에 한 번 속았다.** 처음 6개만 봤을 때는 양쪽 모두 0.0°로 나와 "애니메이션에 없다 →
절차적 구동이다 → 손대지 말라"는 **반대 결론**이 나왔다. 40개로 넓히니 뒤집혔다. 하나의
최대값이 아니라 **몇 %가 움직이는지**를 세야 했다.

#### 고쳤다 — 그리고 세 번 어긋났다

레퍼런스 포즈 기준 로컬 회전 델타를 옮긴다(`TargetLocal = TargetRefLocal · SourceRefLocal⁻¹ · SourceLocal`,
레스트 포즈 정렬기와 같은 후위 곱 형태). 대응은 **트위스트 본이 매달린 역할**로 잡는다.

베이커가 "8개에 73키 기록"이라고 찍는데도 측정은 계속 0.0°였다. 세 단계로 좁혔다.

1. **쓰기가 실패한 것인지부터 확인했다.** 베이커 안에서 되읽어 로그를 남기니 원시 데이터는
   10.4°(원본 10.1°)로 제대로 들어가 있었다. 쓰기는 문제가 아니었다.
2. **베이커와 측정기가 다른 본을 가리키고 있었다.** Manny의 아래팔에는 `lowerarm_twist_01_l`과
   `lowerarm_twist_02_l`이 둘 다 있다. 베이커는 본 배열 순서로 `_02`를, 측정기는 이름 순으로
   `_01`을 골랐다. 양쪽을 **역할 본에 가까운 순**으로 맞췄다. 8개 중 4개가 살아났다.
3. **동점 처리가 또 달랐다.** 두 트위스트 본이 **둘 다 역할 본의 직접 자식**이라 거리가 같았고,
   C++는 배열 순서로, 파이썬은 이름 순으로 동점을 깼다. 동점 규칙을 "이름이 작은 쪽"으로
   통일했다. 8개 전부 살아났다.

전부 "같은 이름표가 서로 다른 본을 가리키는" 종류다. 이 프로젝트에서 세 번째로 같은 모양이다
(정렬기의 마디 한 칸 밀림, 손가락 중수골, 그리고 이것).

| | 전 | 후 |
|---|---|---|
| 트위스트 전달 비 (여덟 역할) | 0.00~0.01 | **1.00** |
| `twist_dropped_worst` | 8 | **0** |
| `twist_ratio_worst_error` | — | **0.013** |

몸통·손가락·접지 지표는 한 자리도 변하지 않았다(0.1° / 8.4°, 동작 왜곡 2.46°, 손가락 0.0°,
발 높이 오차 0.0113, 접지 불일치 0.0312).

트위스트 본이 없는 대상(X_Bot·골렘·늑대)에서는 아무 일도 하지 않는다. `UPT.BakeTwistMotion 0`으로
끌 수 있다 — AnimBP가 트위스트를 구동하는 리그를 쓰게 되면 그때는 꺼야 한다.

## 회귀 기준을 쌍별로 나눴다

두 쌍의 성격이 다르므로(한쪽은 정렬, 한쪽은 미정렬) 합친 중앙값 하나로는 의미가 없다.

```
length_mismatch                                  == 0
pairs                                            >= 4
targets.SKM_Manny.segment_angle_median_deg       <= 5.0
targets.SKM_Manny.worst_segment_deg              <= 14.0
targets.Forest_Golem_1_PolyArt.segment_angle_median_deg <= 22.0
motion_deviation_worst_deg                       <= 3.5
foot_slide_target                                <= 0.13
```

골렘 쪽 기준은 "고치겠다"가 아니라 **"더 나빠지면 안다"** 는 뜻이다.

## 레스트 포즈 정렬을 직접 계산했다 (2026-10-06)

폴백 Rig에서 정렬을 건너뛴 대가가 골렘 쌍의 18.4°였다. 엔진 `AutoAlignBones`는 못 쓰니
**같은 보정을 직접 계산해** 리타기팅 포즈에 써 넣었다(`UPTRestPoseAligner.cpp`).

엔진이 리타기팅 포즈 오프셋을 어떻게 적용하는지부터 확인했다.

```cpp
// IKRetargetProcessor.cpp
const FQuat LocalBoneRotation = RefPoseLocal[BoneIndex].GetRotation() * BoneDelta.Value;
```

로컬 회전에 **뒤에서 곱한다.** 그래서 컴포넌트 공간에서 `Align`만큼 돌리려면 부모 회전으로 감싸
로컬로 되돌려야 한다.

```
Delta = RefLocal⁻¹ · Parent⁻¹ · Align · Parent · RefLocal
```

맞출 방향은 체인의 **누적 길이 비율**로 대응시킨다. 원본은 트위스트 본이 끼어 본 개수가 다르지만,
"체인의 몇 %지점"으로 짝지으면 그대로 맞는다. 본 하나를 돌릴 때마다 아래쪽 위치가 바뀌므로
마디마다 컴포넌트 포즈를 다시 계산한다.

### 결과

| 대상 | 정렬 방식 | 각도 중앙 | 최악 뼈마디 |
|---|---|---|---|
| `Forest_Golem_1_PolyArt` | 없음(이전) | 18.4° | 70.0° |
| `Forest_Golem_1_PolyArt` | **직접 계산** | **6.5°** | **13.3°** |

본 14개를 정렬했고, 어설션 없이 에디터가 살아 있다.

### 엔진 정렬을 완전히 대체할 수 있는지도 재 봤다 — 없었다

직접 계산한 정렬이 엔진 것을 대신할 수 있으면 어설션 나는 API를 아예 안 써도 된다.
그래서 Manny 쪽도 직접 계산으로 바꿔 측정했다.

| Manny 쌍 | 각도 중앙 | 최악 |
|---|---|---|
| 엔진 `AutoAlignBones` | **4.7°** | **11.5°** |
| 직접 계산 | 7.2° | 14.0° |

**엔진이 더 낫다.** 되돌리고 두 경로를 그대로 뒀다. 엔진 Auto Characterizer가 만든 Rig에는 엔진 정렬,
자체 분석 Rig에는 직접 계산한 정렬을 쓴다. 코드는 한 줄 더 복잡해지지만 수치가 그렇게 말한다.

## 동작 표본을 늘렸다

걷기·달리기뿐이던 표본에 **180도 제자리 회전 · 달리며 점프 · 팔 휘두르기**를 넣어
캐릭터 2쌍 × 애니메이션 5개 = **10쌍**으로 만들었다.

| 애니메이션 | Manny | 골렘 |
|---|---|---|
| `Walk_F` | 2.6° | 8.6° |
| `Run_F` | 4.7° | 6.4° |
| `Turn_Standing_180L` | 4.2° | 7.0° |
| `Jump_Running` | 4.7° | 6.5° |
| `Idle_Fidget_Swipe` | 5.1° | 4.5° |

이전에 보고하던 "3.7°"는 걷기·달리기 두 개의 중앙값이었다(2.6과 4.7의 중앙). **표본을 늘리니 4.7°가 됐다.**
수치가 나빠진 게 아니라 **쉬운 동작만 재고 있었던 것**이다.

최악 뼈마디는 10개 전부 `calf→foot`으로 10~13°다. 앞 절에서 본 대로 대부분 고정 오프셋이고,
동작 왜곡은 가장 큰 경우(골렘 팔 휘두르기)가 3.57°다.

## 리타기팅 결과물 폴더를 고쳤다

문서에는 "원본과 같은 폴더에 생성"이라 적혀 있었지만 실제로는 `/Game` 루트에 쏟아지고 있었다.
엔진의 편의 함수 `DuplicateAndRetarget`이 출력 폴더를 인자로 받지 않아
`FNameDuplicationRule`의 기본값(`/Game`)이 그대로 쓰이기 때문이었다.

배치 컨텍스트를 직접 채워 `NameRule.FolderPath`를 설정값으로 지정하도록 바꿨다.
새 설정 `DefaultRetargetedAnimationPath`(기본 `/Game/Animation/UPT/Retargeted`)로 조정한다.
생성된 에셋 목록은 **폴더의 생성 전후를 비교해** 찾는다(이름 충돌 시 엔진이 번호를 붙이므로 예측하지 않는다).

## 접지 지표를 따로 만들었다 (2026-10-06)

앞 절 "남은 것"에 `calf→foot` 10~13°를 고칠 가치가 있지만 **지금 재는 지표가 바로 그 마디라
지표에 맞춰 튜닝이 되기 쉬우니 접지 지표를 먼저 만들어야 한다**고 적어 뒀다. 그걸 만들었다.

각도가 아니라 **높이**를 본다. 발이 바닥에서 얼마나 떠 있는지의 시간별 곡선을 다리 길이로 정규화해
원본과 비교한다. 바닥은 그 클립에서 두 발이 닿은 가장 낮은 지점으로 잡는다.

| 지표 | 뜻 |
|---|---|
| `foot_clearance_error` | 발 높이 곡선의 차이(다리 길이 대비) 중앙값 |
| `foot_clearance_worst` | 쌍 단위 최악값 |
| `contact_mismatch` | 접지 상태(바닥 근처인가)가 원본과 다른 프레임 비율 |

### 만들자마자 계획이 틀렸다는 걸 알려 줬다

| 애니메이션 | 대상 | `calf→foot` | 발 높이 오차 | 접지 불일치 |
|---|---|---|---|---|
| Idle_Fidget_Swipe | 골렘 | 11.6° | **0.1054** | **0.6875** |
| Jump_Running | 골렘 | 13.3° | 0.0380 | 0.0625 |
| Turn_180L | 골렘 | 11.9° | 0.0219 | 0.0417 |
| Walk_F | Manny | 10.4° | **0.0060** | 0.0208 |

**`calf→foot` 각도는 10쌍 전부 9.5~13.3°로 거의 일정한데 접지 오차는 18배 차이가 난다.**
즉 그 각도는 발 디딤 품질을 설명하지 못한다. 고치려던 대상이 틀렸다.
접지 지표를 먼저 만들지 않았다면 각도만 보고 "발이 좋아졌다"고 할 뻔했다.

진짜 문제는 따로 있었다. 서 있는 동작에서 **골렘의 발이 바닥에서 다리 길이의 12~24%만큼 떠 있다.**
원본은 같은 구간에서 0.000으로 완전히 붙어 있다.

### 원인이라고 생각한 것 — 틀렸다

리타기터 op 스택을 덤프해 보니 **기본 스택이 두 벌**이었다
(`Pelvis Motion` / `Pelvis Motion_0`, `FK Chains` / `FK Chains_0` … op 11개).
`IKRetargetFactory`가 이미 넣어 둔 스택 위에 `AddDefaultOps()`를 또 부른 탓이다.
펠비스 보정이 두 번 걸리면 다리 길이 차이에 비례해 발이 뜰 것이고, 그러면
Manny(+6%)에서 거의 안 보이고 골렘(+55%)에서 크게 보이는 것과 맞아떨어진다.

고쳐서 op 11개 → 6개가 됐고, **측정값은 소수점 넷째 자리까지 하나도 바뀌지 않았다.**
중복 op는 실제로 중복 적용되지 않는다. 가설이 틀렸다. 수정 자체는 위생 문제라 유지했지만,
**발 뜨기의 원인은 아니다.**

### 정렬이 접지를 희생하지 않았는지도 확인했다

각도를 좋게 하는 수정이 접지를 망가뜨릴 수 있으므로, `UPT.RestPoseAlign` 콘솔 변수를 넣어
같은 빌드에서 켜고 끄며 쟀다.

| 골렘 · 동작 5개 | 정렬 없음 | 정렬 있음 |
|---|---|---|
| 뼈마디 각도 중앙 | 18.6° | **6.5°** |
| 최악 뼈마디 | 70.0° | **13.3°** |
| 발 높이 오차 중앙 | 0.0409 | **0.0229** |
| 발 높이 오차 최악 | 0.1743 | **0.1054** |
| 접지 불일치 | 0.2708 | **0.0625** |

**맞교환이 아니라 양쪽 다 좋아진다.** 남은 발 뜨기는 정렬이 만든 것이 아니라 정렬이 줄여 준 것이다.

## 원본을 바꿔 봤다 — 오차는 대상만의 문제가 아니었다

같은 대상(골렘)에 원본만 Synty → UE4 마네킹으로 바꿔 4개를 더 돌렸다.

| 조합 | 각도 중앙 | 최악 뼈마디 | 발 높이 오차 |
|---|---|---|---|
| Synty → Manny | 4.7° | 11.5° `calf→foot` | 0.0060~0.0240 |
| Synty → 골렘 | 6.5° | 13.3° `calf→foot` | 0.0219~0.1054 |
| **UE4 마네킹 → 골렘** | **2.4°** | **33.1° `lowerarm→hand`** | 0.0034~0.1793 |

같은 골렘인데 **원본이 바뀌니 중앙값은 좋아지고(6.5 → 2.4) 최악은 나빠졌다(13.3 → 33.1).**
틀어지는 뼈마디도 다리에서 팔로 옮겨 갔다. **오차는 대상 체형만의 함수가 아니다.**
서 있는 동작(`Idle`)의 발 높이 오차는 0.0034로 거의 완벽했는데, 공격 동작(`Combo_A`)은 0.1793이었다.
발 뜨기는 다리 길이보다 **원본이 펠비스를 얼마나 위아래로 움직이는가**에 더 붙어 있다.

그래서 회귀 기준을 **원본→대상 조합별**로 나눴다. 대상만으로 묶으면 두 원본이 섞여 묻힌다.

## 팔 33°의 정체: 마디를 한 칸 밀려 맞추고 있었다 (2026-10-06)

UE4 마네킹 원본 → 골렘에서 팔만 33° 어긋나던 것을 끝까지 봤다. 세 체인의 본 구성을 뽑아 보니
트위스트 본도, 길이 0인 마디도 없는 **깔끔한 3본 체인**이었고 비율도 거의 같았다.

| | 위팔 마디 | 아래팔 마디 | 아래팔 마디 시작 비율 |
|---|---|---|---|
| UE4 마네킹(원본) | 30.34 | 26.98 | **0.529** |
| 골렘(대상) | 67.66 | 62.75 | **0.519** |

여기서 드러났다. 맞출 방향을 고를 때 **대상 마디의 "시작" 비율 이하인 마지막 원본 마디**를
집고 있었다. 골렘 아래팔은 0.519에서 시작하고 원본 아래팔은 0.529에서 시작하므로,
`0.519 ≤ 0.529`가 성립하지 않아 **아래팔이 원본 위팔 방향에 맞춰졌다.**
그 어긋남이 곧 팔꿈치 각도였고, 그래서 모든 애니메이션에서 32~33°로 똑같이 나왔던 것이다.

**마디의 중점끼리 가장 가까운 것을 고르도록** 바꿨다. 섞지 않고 하나를 고르는 건 그대로다
(아래 절의 접선 보간은 섞어서 더 나빠졌다).

| 조합 | 시작 비율로 고를 때 | **중점으로 고를 때** |
|---|---|---|
| UE4 마네킹 → 골렘 | 0.0° / **33.1°** | 0.0° / **4.8°** |
| Synty → X_Bot | 5.2° / 13.9° | **3.8° / 7.1°** |
| Synty → 골렘 | 7.0° / 13.3° | **5.6° / 10.7°** |
| Synty → UE 마네킹(엔진 정렬) | 4.7° / 11.5° | 4.7° / 11.5° (불변) |

엔진 정렬을 쓰는 조합이 그대로인 것이 교차 오염이 없다는 확인이다.
전체 최악 뼈마디가 **33.1° → 11.5°**가 됐다. 기준도 그만큼 조였다.

한 가지는 조금 나빠졌다. 발 높이 오차 최악이 0.1297 → 0.192다(중앙은 0.0227 → 0.0242).
각도가 크게 좋아진 대신 UE4 공격 동작의 발 뜨기가 조금 늘었다. 기준 안이라 두되 기록해 둔다.

## 엔진 정렬 API를 완전히 걷어냈다 (2026-10-06)

한 칸 밀림을 고치고 나서 "직접 계산한 정렬이 엔진보다 2.5° 나쁘다"는 전제를 다시 쟀다.
그 격차의 대부분이 방금 고친 밀림이었다.

| Manny 쌍 (엔진 Rig) | 각도 중앙 | 최악 |
|---|---|---|
| 엔진 `AutoAlignBones` | 4.7° | 11.5° |
| 직접 계산 (밀림 수정 **전**) | 7.2° | 14.0° |
| **직접 계산 (밀림 수정 후)** | **3.3°** | **8.7°** |

이제 직접 계산 쪽이 더 낫다. 그래서 **엔진 `AutoAlignBones` 경로를 코드에서 삭제**하고
모든 조합을 직접 계산으로 통일했다. `bAlignRestPose` 분기도 함께 없앴다.

얻은 것:
- **에디터를 세 번 내린 어설션 경로가 코드에서 사라졌다.** 더는 "이 Rig은 안전한가"를 따질 필요가 없다
- Rig 생성 경로(엔진 Auto Characterizer / 자체 분석)에 따라 갈라지던 분기가 없어졌다
- 전체 최악 뼈마디 11.5° → **10.7°**, 중앙 4.2° → **3.5°**

| 조합 | 각도 중앙 | 최악 뼈마디 |
|---|---|---|
| Synty → UE 마네킹 | **3.3°** | 8.7° |
| Synty → X_Bot (Mixamo) | 3.8° | 7.1° |
| Synty → Forest Golem | 5.6° | 10.7° |
| UE4 마네킹 → Forest Golem | 0.0° | 4.8° |

## 접선 보간을 시도했다 — 되돌렸다

UE4 원본의 팔 33°를 겨냥해, 정렬에서 맞출 방향을 고를 때 **양옆 마디를 섞어 접선을 만드는**
방식을 구현했다(기존에는 길이 비율에 해당하는 마디 하나를 그대로 집었다).

| | 마디 하나(기존) | 접선 보간 |
|---|---|---|
| UE4 → 골렘 최악(팔) | 33.1° | **16.1°** |
| UE4 → 골렘 중앙 | **2.4°** | 4.8° |
| Synty → 골렘 최악 | **13.3°** | 18.1° |
| Synty → 골렘 중앙 | **6.5°** | 6.8° |

겨냥한 팔은 절반이 됐지만 **기준 데이터셋이 전반적으로 나빠졌다.** 원리로도 그렇다 —
관절이 굽어 있으면 위팔 방향과 아래팔 방향을 섞는 셈이라 어느 쪽도 아닌 방향이 나온다.
되돌리고 코드에 이유를 남겼다. 팔 33°는 **알려진 한계**로 기준에 박아 더 나빠지지만 않게 했다.

## 결과물 짝짓기 버그

산출물 폴더를 고치면서 결과를 **폴더의 생성 전후 비교**로 찾도록 바꿨는데, 그 결과 배열을
입력과 **인덱스로 짝지어** manifest를 쓰고 있었다. 폴더 비교 결과의 순서는 입력 순서와 다르고,
이름이 겹치면 엔진이 번호까지 붙인다. 엉뚱한 쌍이 들어가 `length_mismatch`가 4로 튀면서 드러났다.
이름 접두사로 짝짓도록 고쳤다. **회귀 기준에 `length_mismatch == 0`을 넣어 둔 덕에 잡혔다.**

## 발 뜨기를 끝까지 추적했다 — 원인은 못 찾았고, 가설 셋을 기각했다 (2026-10-06)

접지 지표가 드러낸 "서 있는 동작에서 발이 뜬다"를 파고들었다. 먼저 **펠비스 높이 곡선**을
원본과 비교했더니 범인이 한눈에 보였다.

| 조합 | 원본 펠비스 진폭 | 결과 펠비스 진폭 |
|---|---|---|
| Synty → UE 마네킹 | 0.1642 | **0.1636** |
| Synty → Forest Golem | 0.1642 | **0.0000** |
| UE4 마네킹 → Forest Golem | 0.1140 | **0.0000** |
| Synty → X_Bot (Mixamo) | 0.1642 | **0.0000** |

**네 조합 중 UE 표준끼리인 하나만 수직 펠비스 이동이 전달된다.** 나머지 셋은 정확히 0이다.
몸이 위아래로 움직이지 않으니 원본이 몸을 낮추는 구간에서 다리가 그 차이를 떠안고 발이 뜬다.
발 높이 오차가 **원본이 펠비스를 얼마나 움직이는 동작인가**에 비례했던 것과 정확히 맞는다
(`Idle_RM` 진폭 0.008 → 오차 0.0034, `Combo_A` 진폭 0.349 → 오차 0.1793).

### 기각한 가설 셋

| 가설 | 검증 | 결과 |
|---|---|---|
| 기본 op 스택이 두 벌이라 펠비스 보정이 두 번 걸린다 | op 11개 → 6개로 수정 후 재측정 | **수치가 소수점 넷째 자리까지 동일.** 중복 op는 적용되지 않는다 |
| 내가 넣은 레스트 포즈 정렬이 원인이다 | `UPT.RestPoseAlign` 0/1로 A/B | **정렬이 오히려 접지를 0.0409 → 0.0229로 개선.** 원인이 아니라 완화 요인 |
| 리타기팅 루트를 잘못 골랐다 | 골렘 계층이 `Root → CG → Pelvis`이고 `Pelvis`의 로컬 오프셋이 0이다. 높이는 `CG`가 든다. 루트를 `CG`로 바꿔 재측정 | **`CG`가 149.89에 고정된 채 그대로.** 루트 선택 문제가 아니다 |

### 더 좁혀 본 것 (2026-10-06 추가)

**op 자체가 실행되지 않는다**는 것까지 확인했다. Pelvis Motion 설정에 정적 오프셋
`translation_offset_global = (0,0,100)`을 넣고 돌려 보면,

| | 결과 |
|---|---|
| Manny | 펠비스 z 76.87 → **176.87** (오프셋 반영됨) |
| 골렘 | 0.00 → **0.00** (아무 변화 없음) |

하류 op이 덮어쓰는 것도 아니다. **Pelvis Motion 하나만 켜고** 나머지를 전부 꺼도 결과가 같다.
엔진 소스상 op은 `IsEnabled() && IsInitialized()`일 때만 실행되고, 설정의 pelvis 본 이름은
양쪽 다 올바르다(`source=pelvis`, `target=Pelvis` — 둘 다 실제 존재하는 본).
초기화 실패 경고도 로그에 없다. `IsInitialized()`가 왜 거짓인지는 엔진을 소스 빌드로
계측하지 않으면 더 좁힐 수 없는 지점이다.

### 네 번째 가설도 기각: 폴백 원본 Rig

실패하는 세 조합은 모두 **원본 Rig까지 폴백**을 쓰고 있었다(한쪽만 엔진 Characterize에 실패해도
빌더가 양쪽 다 폴백으로 내리기 때문). 그래서 "쪽마다 더 나은 Rig을 고르면 되지 않을까" 싶어
엔진 Rig이 만들어진 쪽은 그대로 쓰도록 바꿔 봤다.

| 조합 | 기존(양쪽 폴백) | 쪽별 선택 |
|---|---|---|
| Synty → 골렘 | 5.6° | **31.0°** |
| Synty → X_Bot | 3.8° | **31.1°** |
| UE4 → 골렘 | 0.0° | **14.3°** |

**전면적으로 나빠졌다.** 두 Rig의 체인 **이름 규칙**이 달라져 `AutoMapChains(Exact)`가 거의
아무것도 짝짓지 못한다. 펠비스 이동도 여전히 0이었다. 되돌렸고, "한쪽이 폴백이면 양쪽 다 폴백"인
현재 구조가 맞다는 것을 코드 주석으로 남겼다. **회귀 기준이 10건 실패로 즉시 잡아 줬다.**

### 우리 코드 문제가 아니라는 것은 확인했다

플러그인을 거치지 않고 **엔진 기본 API**(`UIKRetargetBatchOperation.duplicate_and_retarget`)로
같은 리타기터·같은 애니메이션을 직접 돌렸다. 결과는 같다 — 골렘 `Pelvis` 로컬 z가 0.00으로 고정이다.
**우리 설정이 아니라 엔진이 이 조합에서 수직 이동을 만들지 않는다.**

### 지금 상태

원인은 아직 모른다. 다만 **경계가 숫자로 그어져 있다.**

- 어떤 조합에서 일어나는지: 대상이 UE 표준 계층(`root`(고정) → `pelvis`(높이를 든 로컬 오프셋))이
  아닌 경우. 골렘은 사이에 `CG`가 끼고, X_Bot은 `Hips`가 최상위 본이라 고정된 부모가 없다.
- 얼마나 나쁜지: 발 높이 오차 중앙 0.023, 최악 0.13 (다리 길이 대비)
- 무엇이 원인이 **아닌지**: 위 표의 셋
- 회귀로 잠겨 있으므로 더 나빠지면 바로 드러난다

다음에 볼 것은 Pelvis Motion op이 실제로 어떤 값을 쓰는지(`scale_vertical`·`affect_ik_vertical`의
의미와, 대상 펠비스의 "지면 대비 높이"를 무엇으로 계산하는지)다.

## 펠비스 이동을 후처리로 직접 구워 넣었다 (2026-10-06)

원인을 끝내 못 찾았으니 **증상을 직접 고치기로** 했다. 엔진 op이 하려던 계산(PelvisMotionOp.cpp)을
그대로 다시 해서 결과 애니메이션의 트랙에 써 넣는다(`UPTPelvisMotionBaker.cpp`).

```
normalized = 원본 펠비스 컴포넌트 위치 / 원본 레퍼런스 펠비스 높이
대상 펠비스 컴포넌트 위치 = normalized * 대상 레퍼런스 펠비스 높이
```

**이미 이동이 들어 있는 결과는 건드리지 않는다.** 엔진 op이 정상 동작한 조합(Synty→Manny)은
그대로 두고, 세 축 모두 0으로 나온 경우에만 채운다. `UPT.BakePelvisMotion`으로 끄거나(0)
강제로 덮어쓸 수 있다(2).

### 가는 길에 두 번 틀렸다

**1) 합성 순서를 거꾸로 썼다.** UE의 규칙은 `자식 컴포넌트 = 자식 로컬 × 부모 컴포넌트`인데
잎에서 루트로 올라가며 `부모 × 누적`으로 곱했다. 높이 비율이 **-0.000**으로 찍혀서 바로 드러났다.
로그에 비율을 같이 남겨 둔 덕에 한 번에 보였다.

**2) 엉뚱한 본에 썼다.** 분석기가 Pelvis로 뽑은 본이 **높이를 들고 있지 않았다.**
Forest Golem은 계층이 `Root → CG → Pelvis`이고 `Pelvis`의 로컬 이동이 (0,0,0)이다.
높이는 `CG`가 든다. 원시 키는 분명히 기록되는데 샘플링하면 계속 0이 나와 한참 헤맸다.

결정적 단서는 **회전**이었다. 같은 애니메이션에서

| 본 | 회전 | 이동 |
|---|---|---|
| `L-Thigh` | 변함 | 고정(정상 — 회전만 전달) |
| `Pelvis` | **고정 90°** | 고정 |
| `CG` | **변함** | 고정 |

리타기터가 실제로 구동하는 몸통 본은 `CG`였다. 그 본에 이동을 써야 몸이 움직인다.
→ 레퍼런스 포즈에서 로컬 이동이 거의 0인 동안 부모로 거슬러 올라가 **높이를 드는 본**을 고르도록 했다.
UE 마네킹(`pelvis` 로컬 z=95.9)과 Mixamo(`Hips`가 최상위)는 그대로 유지된다.

(압축 재생성을 `CacheDerivedDataForCurrentPlatform()`으로 직접 부르는 것도 시도했는데
**재진입 루프에 빠져 에디터 메모리가 19.7GB까지 치솟고 멎었다.** 표준 경로인 `PostEditChange()`로 바꿨다.)

### 결과

각도 지표는 **한 자리도 변하지 않았다**(이동만 건드렸으므로 당연하고, 그것이 확인이기도 하다).

| 지표 | 전 | 후 |
|---|---|---|
| 발 높이 오차 중앙 | 0.0242 | **0.0113** |
| 발 높이 오차 최악 | 0.192 | **0.0413** |
| 접지 불일치 | 0.0625 | **0.0417** |
| 발 미끄러짐(원본 0.0391) | 0.0708 | **0.0428** |
| 뼈마디 각도 중앙 / 최악 | 3.5° / 10.7° | 3.5° / 10.7° |

**서 있는 동작에서 다리 길이의 19%까지 떠 있던 발이 4%로 내려왔다.** 미끄러짐도 원본 수준에 붙었다.
회귀 기준을 그만큼 조였다(`foot_clearance_worst` 0.20 → 0.06 등).

에디터에서 골렘 달리기를 재생해 **눈으로도 확인했다** — 몸이 위아래로 제대로 출렁인다.
이전에는 몸이 고정된 채 발만 공중에서 움직였다. 지표와 보이는 결과가 일치한다.

### 남은 한계

증상을 고친 것이지 원인을 고친 것이 아니다. 엔진 op이 왜 실행되지 않는지는 여전히 모르고,
베이커는 그 위에 덧씌우는 보정이다. op이 어느 날 정상 동작하면 베이커는 자동으로 비켜선다
(이미 이동이 있으면 건드리지 않으므로).

## 같은 에셋을 다시 쓰도록 고쳤다 — 중복이 쌓이던 문제 (2026-10-06)

리타기팅을 돌릴 때마다 IK Rig·리타기터·결과 애니메이션이 **새로 만들어지고 있었다.**
엔진이 이름 충돌을 피해 `..._1`, `..._2`를 붙이는 바람에, 몇 번만 돌려도
메시 하나에 Rig이 대여섯 개씩 쌓였다(**21개까지 확인**).

| | 전 | 후 |
|---|---|---|
| IK Rig | 실행마다 +N | 같은 이름이 있으면 **재사용**(체인만 비우고 다시 채움) |
| 리타기터 | 실행마다 +1 | 같은 이름이 있으면 **재사용** |
| 결과 애니메이션 | 실행마다 +N | `bOverwriteExistingFiles=true`로 **덮어쓰기** |

같은 명령을 3회 반복해 확인했다. IK Rig 5개, 리타기터 1개, 결과물 2개로 **고정**된다.

### 같이 처리한 것

- 리타기터를 재사용하면 **지난번 레스트 포즈 정렬 오프셋이 남는다.** 이번에 맞추지 않는 본의 값이
  섞이지 않도록, 재사용일 때는 리타기팅 포즈를 먼저 초기화한다.
- 결과물을 덮어쓰면서 이름이 `<원본 이름><접미사>`로 정해지므로, 생성 결과를 찾던
  **폴더 비교 방식을 걷어냈다.** 그 방식은 순서가 입력과 달라 manifest에 엉뚱한 쌍을 넣은 적이 있다
  (`length_mismatch`가 4로 튀어 잡혔다). 이제 이름으로 바로 찾는다.

전체 19쌍 측정값은 **소수점까지 동일**하다. 에셋 관리만 바뀌고 결과는 그대로다.

## 원인을 찾았다 — 우리가 펠비스를 FK 체인에 가두고 있었다 (2026-10-06)

소스 빌드까지 가기 전에 한 가지가 남아 있었다. 지금까지의 비교는 **메시가 서로 달라** 오염돼 있었다.
"엔진 Rig은 되고 폴백 Rig은 안 된다"를 보려면 **같은 메시**로 둘을 비교해야 한다.
그러려고 `UPT.ForceFallbackRig` 스위치를 넣었다.

| SKM_Manny, 같은 애니메이션 | pelvis 이동 진폭 |
|---|---|
| 엔진 Characterize Rig | X 8.75 / Y 9.91 / Z 11.23 |
| 폴백(자체 분석) Rig | **0.00 / 0.00 / 0.00** |

**메시도 리타기터도 엔진도 아니었다. 우리 Rig 구성이었다.** 그러면 두 Rig을 그냥 비교하면 된다.

| 체인 | 엔진 Characterize | 우리 폴백 |
|---|---|---|
| `Root` | `root → root` | **`root → pelvis`** |
| `Spine` | `spine_01 → spine_05` | `spine_01 → head` |
| `Neck` | `neck_01 → neck_02` | `neck_01 → head` |
| `Head` | `head → head` | (없음) |

**`Root` 체인을 `root → pelvis`로 잡은 탓에 펠비스가 FK 체인 안에 들어가 있었다.**
FK 체인 리타기팅은 회전만 옮기므로, Pelvis Motion op이 써 넣은 이동이 레스트 포즈 값으로 덮인다.
엔진 관례는 `Root` 체인이 루트 본 하나뿐이고, 펠비스는 Pelvis Motion op에게 맡기는 것이다.

### 세 가지를 고쳤다

1. **`Root` 체인을 루트 본 하나로** 줄였다. → Manny 폴백 Rig이 엔진 Rig과 **완전히 같은 값**(8.75/9.91/11.23)이 됐다.
2. **리타기팅 루트를 '높이를 드는 본'으로** 고르게 했다. 골렘은 `Root → CG → Pelvis`이고 `Pelvis`의
   로컬 이동이 (0,0,0)이라 높이를 `CG`가 든다. 레퍼런스 포즈의 로컬 이동이 0인 동안 부모로 올라간다.
   → 골렘 `CG` 진폭 **15.50/13.67/17.56**. 후처리 베이커가 계산하던 값과 **소수점까지 같다**(교차 검증).
3. **`Root`를 필수 체인에서 뺐다.** 엔진 Auto Characterizer도 Mixamo처럼 별도 루트 본이 없는 리그에서는
   Root 체인을 만들지 않는다(X_Bot 확인). 필수로 걸어 둔 탓에 **X_Bot이 엔진 Rig을 못 쓰고 폴백으로
   내려가고 있었다.** 더불어 폴백에서도 리타기팅 루트 하나뿐인 Root 체인은 만들지 않도록 했다.
   → X_Bot `Hips` 진폭 **9.51/10.78/12.21**, 그리고 이제 엔진 Rig을 쓴다.

### 결과

| 조합 | 펠비스 이동(베이커 끈 상태) |
|---|---|
| Synty → Manny | 8.75 / 9.91 / 11.23 |
| Synty → 골렘 | 15.50 / 13.67 / 17.56 |
| Synty → X_Bot | 9.51 / 10.78 / 12.21 |

**후처리 베이커는 이제 아무것도 쓰지 않는다.** 이미 이동이 있으면 비켜서도록 만들어 뒀고,
로그에 기록 줄이 하나도 찍히지 않는 것으로 확인했다. 엔진 op이 제 일을 하므로 베이커는 대기 상태다.
전체 19쌍 수치는 그대로이거나 더 낫다(X_Bot 중앙 3.8° → **3.4°**).

### 돌아보면

"원인을 못 찾겠으니 증상을 고치자"고 베이커를 만든 것이 결과적으로 맞았다.
그 과정에서 **높이를 드는 본을 찾는 규칙**을 만들었고, 그게 그대로 2번 수정의 핵심이 됐다.
베이커가 계산하던 값과 엔진 op이 내놓은 값이 소수점까지 같다는 것이, 둘 다 맞다는 확인이기도 하다.

## 체인을 엔진 관례대로 끊었다 — 그리고 정렬기의 구멍이 드러났다 (2026-10-06)

앞 절에서 Root 체인을 고치면서 나머지 차이도 눈에 들어왔다. 우리 `Spine` 체인은 **머리까지 삼키고**
있었고, `Neck`도 머리에서 끝나 **같은 본이 세 체인에 동시에** 들어가 있었다.

| 체인 | 엔진 Characterize | 우리(수정 전) | 우리(수정 후) |
|---|---|---|---|
| `Spine` | `spine_01 → spine_05` | `spine_01 → head` | **`spine_01 → spine_05`** |
| `Neck` | `neck_01 → neck_02` | `neck_01 → head` | **`neck_01 → neck_02`** |
| `Head` | `head → head` | (없음) | **`head → head`** |

역할 목록에 "척추 끝"이 없으므로, **다음 체인 시작 본의 부모**까지로 끝을 줄이는 방식으로 구했다
(목이 있으면 목의 부모, 없으면 머리의 부모). 엔진이 내놓는 구성과 같아진다.

### 고치니 한쪽이 나빠졌다

| 골렘 조합 | 체인 수정 전 | 체인 수정 후 |
|---|---|---|
| 뼈마디 각도 중앙 | 5.6° | **2.0°** |
| 최악 뼈마디 | 10.7° | **31.6°** (`neck→head`) |

몸통은 좋아졌는데 **머리가 크게 틀어졌다.** 원인은 체인 구성이 아니라 **내 정렬기**였다.
`Neck → Neck`, `Head → Head`처럼 **본이 하나뿐인 체인은 방향을 만들 수 없어** 정렬에서 통째로 빠진다.
전에는 `Neck → Head`가 두 본짜리라 우연히 정렬되고 있었던 것이다.

→ 한 본 체인은 **바로 아래로 이어지는 다른 매핑된 체인의 시작 본까지 한 칸 늘려** 방향을 만들게 했다.
양쪽 모두 같은 이름의 체인을 쓰므로 대응이 어긋나지 않는다.

### 결과

| 조합 | 체인 수정 전 | 최종 |
|---|---|---|
| Synty → UE 마네킹 | 3.3° / 8.7° | 3.3° / 8.7° |
| Synty → Forest Golem | 5.6° / 10.7° | **0.6° / 7.8°** |
| Synty → X_Bot (Mixamo) | 3.4° / 7.1° | **0.8° / 7.1°** |
| UE4 마네킹 → Forest Golem | 0.0° / 4.8° | 0.0° / 4.8° |
| **전체 중앙 / 최악** | 3.4° / 10.7° | **0.7° / 8.7°** |

동작 왜곡도 3.13° → **2.46°**. 접지 지표는 그대로다(0.0113 / 0.0413 / 0.0417).

**체인을 엔진 관례대로 끊는 것만으로는 부족했고, 정렬기가 한 본 체인을 다루지 못한다는 구멍을
같이 메워야 효과가 났다.** 중간 측정이 없었다면 "체인 수정은 최악값을 3배로 만든다"고 결론 내고
되돌렸을 것이다.

## 정렬 기준을 체인에서 역할 그래프로 옮겼다 (2026-10-06)

앞 절의 결론을 다시 읽으면 고친 것이 **증상**이었다. 한 본 체인에 구멍이 있던 것도,
그 구멍을 "다른 체인의 시작 본까지 한 칸 늘려" 메운 것도, 전부 **정렬기가 체인을 보고 있기 때문에**
생긴 일이다. 체인은 Rig을 만든 사람이 정하는 것이고, 뼈마디 방향은 스켈레톤이 정하는 것이다.
기준이 잘못된 곳에 걸려 있었다.

| | 체인 기준 (이전) | 역할 그래프 (지금) |
|---|---|---|
| 무엇을 따라 도는가 | `IKRig->GetRetargetChains()` | 해부학적 인접 관계 17마디 |
| 대응을 어떻게 잡는가 | 같은 **이름의 체인**끼리, 누적 길이 비율로 | 같은 **역할**끼리 직접 |
| Rig 구성에 따라 결과가 | 바뀐다 | 바뀌지 않는다 |
| 한 본 체인 | 정렬에서 빠진다(특례 필요) | 개념 자체가 없다 |
| 체인 경계를 넘는 마디 | 정렬이 닿지 않는다 | 그냥 한 마디다 |

정렬기는 이제 `UIKRigDefinition`을 **인자로 받지도 않는다.** 두 메시의 레퍼런스 스켈레톤과
분석기의 역할 대응만 쓴다. Rig 독립성이 주석이 아니라 함수 시그니처로 보장된다.

구현에서 새로 필요해진 것은 두 가지다.

- **자식이 여럿인 본.** 척추에는 목과 양 쇄골이, 펠비스에는 척추와 양 허벅지가 붙는다.
  회전 하나로 전부 맞출 수 없으므로 자식마다 필요한 회전을 구해 평균(누적 slerp)한다.
  체인을 돌 때는 한 줄기씩만 보았으니 생기지 않던 문제다.
- **처리 순서.** 부모를 먼저 맞춰야 자식의 현재 방향이 제대로 나온다. 계층 깊이로 정렬해 돈다.

이름 근거 없이 위치·계층만으로 배정된 역할(`ForcedRoles`)은 **쓰지 않는다.** 부분 메시에서는
남은 아무 본이나 집어 오므로(`LeftFoot ← jaw`) 그 방향에 맞추면 몸이 통째로 틀어진다.
쇄골이나 목이 없는 리그는 한 칸 건너뛴 역할로 대체한다(`Clavicle → UpperArm`, `Neck → Head`).

### 결과

| 조합 | 체인 기준 | 역할 그래프 |
|---|---|---|
| Synty → UE 마네킹 | 3.3° / 8.7° (`neck→head`) | **0.9° / 8.4°** (`calf→foot`) |
| Synty → Forest Golem | 0.6° / 7.8° | 0.6° / 7.8° |
| Synty → X_Bot (Mixamo) | 0.8° / 7.1° | 1.0° / 7.1° |
| UE4 마네킹 → Forest Golem | 0.0° / 4.8° | 0.0° / **3.2°** |
| **전체 중앙 / 최악** | 0.7° / 8.7° | **0.6° / 8.4°** |

접지 지표와 동작 왜곡은 그대로다(2.46° / 0.0114 / 0.0413 / 0.0417). 12개 스위트 모두 통과.

Manny 중앙값이 3.3° → 0.9°로 떨어진 것이 핵심이다. 남아 있던 `neck→head` 8.7°는 **지표를
고치지 않고** 사라졌다. 정렬기가 `neck_01→neck_02`(체인)를 맞추고 지표는 `neck_01→head`(마디)를
재던 불일치가, 둘 다 같은 역할 마디를 보게 되면서 없어졌다.

### Rig 구성을 바꿔도 같은지 실제로 재 봤다

이것이 이번 변경의 핵심 주장이므로 측정으로 확인했다. `UPT.ForceFallbackRig 1`은 엔진
Characterize가 성공하는 메시에도 **자체 분석 Rig**을 쓰게 한다. 같은 스켈레톤, 전혀 다른 체인 구성이다.

| | 엔진 Characterize Rig | 자체 분석 Rig 강제 |
|---|---|---|
| 정렬한 본 수 (Manny / 골렘 / X_Bot) | 13 / 13 / 11 | **13 / 13 / 11** |
| Synty → UE 마네킹 | 0.9° / 8.4° | 0.7° / 6.1° |
| Synty → Forest Golem | 0.6° / 7.8° | 0.6° / 7.8° |
| Synty → X_Bot | 1.0° / 7.1° | 1.0° / 7.1° |
| UE4 마네킹 → Forest Golem | 0.0° / 3.2° | 0.0° / 3.2° |
| 전체 중앙 / 최악 | 0.6° / 8.4° | 0.6° / **7.8°** |
| 동작 왜곡 | 2.46° | 2.27° |

**정렬한 본 수가 세 대상 모두 똑같다.** 정렬 자체는 Rig 구성에 전혀 반응하지 않았고, 남은 차이는
리타기팅 op의 체인 매핑에서 온 것이다(그리고 나쁘지 않은 쪽으로). 체인 기준이었을 때는 체인 구성을
건드리는 것만으로 최악값이 10.7° → 31.6°로 튀었다.

### 뼈마디별로 뜯어보니 오차가 세 곳에만 몰려 있었다

전체 중앙값만 보면 0.6°라 끝난 것처럼 보이는데, 19쌍의 뼈마디별 수치를 모아 보니 모양이 분명했다.

| 뼈마디 | 중앙 | 최악 |
|---|---|---|
| `thigh→calf`, `upperarm→lowerarm`, `neck→head` | 0.0~0.1° | 0.1~0.4° |
| `pelvis→spine` | 3.4° | 4.6° |
| `lowerarm→hand` | 2.1° | 5.7° |
| `calf→foot` | 5.1° | 7.8° |

**거의 모든 마디가 0.1° 이하인데 세 마디만 남았다.** 평균값에 묻혀 보이지 않던 구조다.

`pelvis→spine`의 원인은 금방 나왔다. **자식이 여럿인 본은 펠비스뿐이다**(척추와 양 허벅지).
회전 하나로 셋을 떠안으니 평균이 셋 중 어느 것도 아닌 값이 된다.

그런데 평균을 어떻게 잘 내느냐가 문제가 아니었다. **갈라지는 방향은 회전으로 고칠 수 있는
성질이 아니다.** 허벅지가 펠비스에서 어느 쪽으로 뻗어 있는지는 골반 폭, 즉 **위치**의 문제다.
펠비스를 돌려 그 방향에 맞춰도 다리 자체의 방향은 어차피 허벅지 본을 돌려 따로 맞춘다.
갈라지는 마디를 정렬에 넣으면 **몸통 방향만 희생되고 얻는 것이 없다.**

→ 역할 그래프를 **축**(한 줄기)의 모음으로 바꿨다. 몸통(펠비스→척추→목→머리), 양팔
(쇄골→위팔→아래팔→손), 양다리(허벅지→정강이→발). 각 본은 **자기 축의 다음 역할**만 본다.
갈라지는 마디(`Pelvis→Thigh`, `Spine→Clavicle`)는 넣지 않는다. 그러면 한 본에 마디가 하나씩
붙으므로 평균이 필요 없어진다.

| 뼈마디 | 갈라지는 마디 포함 | 축만 |
|---|---|---|
| `pelvis→spine` | 3.4° / 4.6° | **0.0° / 0.0°** |
| 조합별 중앙 (Manny/골렘/X_Bot/UE4) | 0.9 / 0.6 / 1.0 / 0.0 | **0.1 / 0.1 / 0.1 / 0.0** |
| 전체 중앙 | 0.6° | **0.1°** |
| 전체 최악 | 8.4° (`calf→foot`) | 8.4° (`calf→foot`) |
| UE4 → 골렘 최악 | 3.2° | **2.6°** |

접지 지표는 사실상 그대로다(0.0114 → 0.0120, 최악 0.0413 동일, 접지 불일치 0.0417 동일).

### 손·발에 남은 오차: IK가 아니었다 (가설 기각)

`calf→foot`과 `lowerarm→hand`만 남았다. 둘 다 **IK Goal이 걸린 본**이라, IK 패스가 발을 바닥에
맞추면서 각도를 바꾸는 것이라고 생각했다. 그러면 "각도 오차가 곧 접지 품질의 대가"라는 뜻이 되므로
고칠 것이 아니라 설명할 것이 된다.

확인용으로 `UPT.DisableIKOps`를 넣고(이름에 IK가 들어간 op을 모두 끈다) 19쌍을 다시 쟀다.

| | IK op 켬 | IK op 끔 |
|---|---|---|
| `calf→foot` | 5.7° / 8.4° | 5.7° / 8.4° |
| `lowerarm→hand` | 2.1° / 5.7° | 2.1° / 5.7° |
| 발 높이 오차 / 접지 불일치 | 0.0120 / 0.0417 | 0.0120 / 0.0417 |

**소수점 둘째 자리까지 하나도 변하지 않았다.** 가설 기각이다. 덤으로 알게 된 것이 하나 더 있다 —
이 조합들에서 IK op은 **아무 일도 하지 않고 있다.** 접지 지표조차 꿈쩍하지 않았으니, 지금까지의
접지 품질은 전부 FK와 펠비스 쪽에서 나온 것이다.

### 원인은 FK 체인의 회전 보간이었다

기각하고 나서 남은 마디를 다시 보면 규칙이 정확하다.

| 마디 | 부모 본이 체인에서 몇 번째인가 | 오차 |
|---|---|---|
| `thigh→calf`, `upperarm→lowerarm`, `neck→head` | **첫 번째** | 0.1° 이하 |
| `calf→foot`, `lowerarm→hand` | 두 번째·세 번째 | 2.1°~5.7° |

FK Chains op의 기본 회전 모드가 `Interpolated`다. 양쪽 체인을 **길이로 정규화**한 뒤 같은 비율
위치의 회전을 이웃 본 사이에서 보간해 가져온다. 체인의 첫 본은 비율 0이라 정확히 오지만,
두 번째 본부터는 허벅지:정강이 길이 비가 다르면 **원본의 다른 본 쪽으로 밀린 값**이 온다.
내가 정렬기에서 직접 겪었던 "마디 한 칸 밀림"과 **같은 종류의 오차**이고, 여기서는 엔진의 의도된 동작이다.

본 개수가 같으면 비율로 찾을 이유가 없다. `One to One`은 i번째를 i번째로 옮긴다.
→ 원본·대상 체인의 **본 개수가 같을 때만** 회전 모드를 `One to One`으로 바꾸게 했다
(개수가 다르면 트위스트 본 유무 등이라 비율 보간이 여전히 맞다). 19쌍에서 체인 10~19개가 바뀌었다.

### 각도는 완벽해졌는데 접지가 나빠졌다 — 그래서 기본으로 켜지 않았다

| 지표 | `Interpolated`(기본) | `One to One` |
|---|---|---|
| 뼈마디 각도 중앙 / 최악 | 0.1° / 8.4° | **0.0° / 0.1°** |
| 동작 왜곡 | 2.46° | **0.01°** |
| 발 미끄러짐 (원본 0.0391) | 0.0427 | **0.0389** |
| 발 높이 오차 | **0.0120** | 0.0181 |
| 발 높이 오차 최악 | **0.0413** | 0.0511 |
| 접지 불일치 | **0.0417** | 0.0625 |

각도 쪽은 사실상 완벽해진다 — 최악 뼈마디 8.4° → **0.1°**, 동작 왜곡 2.46° → **0.01°**.
그런데 접지 불일치가 0.0625로 **회귀 기준(0.06)을 넘는다.**

이유는 분명하다. 회전을 정확히 복사하면 **뼈 길이가 다른 몸에서는 발이 닿는 높이가 달라진다.**
길이 정규화가 그 차이를 메워 주고 있었던 것이고, 그걸 없애니 각도는 맞고 발이 떴다.

**기준을 풀어서 통과시키지 않았다.** 접지 지표는 각도 지표가 품질을 설명하지 못한다는 것을
알고 나서 만든 것이고(위 "접지 지표를 따로 만들었다" 절), 그 지표가 지금 정확히 자기 일을 했다.
`One to One`은 **각도 지표를 0으로 만들면서 실제 품질은 떨어뜨리는 변경**이다. 각도 0.0°는
"원본 회전을 복사했다"는 뜻 이상이 아니고, 그 지표는 여기서 **포화해 더 이상 구분력이 없다.**

→ `UPT.FKOneToOne`은 기본 **끔**이다. 각도 충실도가 접지보다 중요한 경우(예: 같은 체형끼리
옮길 때)에 쓸 수 있도록 스위치로 남겨 두고, 수치를 양쪽 다 적어 둔다.
둘을 모두 얻으려면 `One to One` + 바닥 제약(`FloorConstraintOp`)이나 접지 고정(`SpeedPlantingOp`)을
기본 스택에 넣어 따로 재야 한다. 그것이 다음 단계다.

### 측정 진입점도 묶었다

조합 네 개를 손으로 치다 보니 이번에도 한 번 당했다. `-ExecCmds`는 **에셋 레지스트리 스캔이
끝나기 전에** 실행된다. 그 상태로 돌리면 애니메이션의 Skeleton으로 원본 메시를 역추적하는 조회가
전부 실패해 네 조합 모두 **0쌍 manifest**로 저장된다. 에러 없이 파일이 생기므로 성공처럼 보인다.

→ `Tools/eval/editor/upt_run_retarget_suite.py`에 조합 목록을 넣고, 레지스트리 완료를 기다린 뒤
네 조합을 돌리고 바로 촬영까지 한다. manifest 쌍 수가 기대와 다르면 에러를 남긴다.
회귀 기준에도 전체 지표 두 줄을 넣어, 한 조합이 좋아지고 다른 조합이 나빠지는 변화가 통과하지 않게 했다.

## 다르게 리깅된 사족·비인간 쌍을 실제로 만들어 재 봤다 (2026-10-13)

"남은 것"에 **어려운 사족 쌍**을 적어 두고 "서로 다르게 리깅된 사족 에셋이 없다"고 했다.
그게 틀렸다 — 프로젝트에 이미 들어와 있었다. Fab 라이브러리에서 받아 둔 크리처 팩들을
훑어 보니 사족이 넷 더 있었고, 그중 둘은 **팔다리를 사람 비유가 아니라 위치로 부르는**
완전히 다른 리그였다.

| 에셋 | 본 | 앞다리 이름 | 뒷다리 이름 |
|---|---|---|---|
| `Wolf_Pa_v2` (3ds Max biped) | 58 | `L_UpperArm` `L_Forearm` `L_Hand` | `L_Thigh` `L_Calf` `L_HorseLink` `L_Foot` |
| `Polygonal_Wolf_Black` | 37 | `RigFLLeg1` `RigFLLeg2` `RigFLLegAnkle` | `RigBLLeg1..3` `RigBLLegAnkle` |
| `Polygonal_Dragon` | 68 | `RigLFrontLeg1` `RigLFrontLeg2` `RigLFrontLegAnkle` | `RigLBackLeg1` `RigLBackLeg2` `RigLBackLegAnkle` |
| `Rat` (Easy Animated Enemy Pack) | 43 | `FrontUpLeg_L` `FrontLowLeg_L` `FrontFoot_L` | `BackUpLeg_L` `BackLowLeg_L` `BackFoot_L` |

### 위치 이름은 하나도 읽히지 않고 있었다

`Polygonal_Wolf_Black`의 준비도는 **0.1875**였고, 매핑은 이랬다.

```
LeftUpperArm  <- RigSpine3      RightLowerArm <- RigFLLeg1
LeftLowerArm  <- RigRibcage     RightHand     <- RigFLLeg2
LeftHand      <- RigNeck2       RightThigh    <- RigFLLegAnkle
```

좌우가 뒤섞이고 척추가 팔로 들어갔다. 등급이 C라 **자동 경로에서는 거부됐으니 틀린 결과가
새어 나가지는 않았다.** 그래도 같은 몸을 쓰는 두 리그가 서로 리타기팅되지 않는다는 뜻이다.

대응 규칙은 짐작이 아니라 **다른 리거가 손으로 한 것**을 따랐다. `Wolf_Pa_v2`를 만든 쪽은
앞다리를 `UpperArm`·`Forearm`·`Hand`로, 뒷다리를 `Thigh`·`Calf`·`Foot`로 이름 붙였다.
그래서 **앞다리 = 팔 역할, 뒷다리 = 다리 역할**, 관절은 1→위팔/넓적다리, 2→아래팔/정강이,
`Ankle`→손/발로 잡았다. `Foot1`·`Foot2`는 발가락이라 비워 둔다.

맞는 규칙인지 확인할 수 있는 지점이 있었다 — **체인 길이**. 이 규칙으로 두 늑대의 앞다리가
3대3, 뒷다리가 4대4로 맞는다(`RigBLLeg3` ↔ `L_HorseLink`). 사람↔사람 쌍과 같은 조건이다.

어순은 네 가지를 모두 받는다(`FLLeg1` / `LFrontLeg1` / `LLegFront1` / `FrontUpLeg_L`).
좌우 부호 추정(`IsLikelyLeftName`)에도 같은 꼴을 넣었다. 그게 없으면 왼쪽 본이 하나도
식별되지 않아 기본값으로 추측하고, 맞는 본에 음수 공간 점수가 붙는다.

| 에셋 | 준비도 전 | 후 | 등급 | 자세 판정 |
|---|---|---|---|---|
| `Polygonal_Wolf_Black` | 0.1875 | **0.9375** | C → A | 사족 (유지) |
| `Polygonal_Dragon` | 0.1875 | **0.9375** | C → A | 사족 (유지) |
| `Polygonal_Treant` | 0.3125 | 0.6875 | C (유지) | 사족 |
| `Rat` | 0.25 | 0.4375 | C (유지) | 이족 → **사족** (교정) |
| `Frog` | 0.25 | 0.4375 | C (유지) | 이족 → **사족** (교정) |
| `Spider` | 0.125 | 0.0625 | C (유지) | 이족 → **사족** (교정) |

늑대와 드래곤은 16개 역할이 **좌우 대칭으로, 강제 배정 0개로** 붙었다. 쥐도 매핑은 16개가
전부 맞는데 준비도가 0.4375에 머문다 — 아홉 역할이 신뢰도 0.40이고 준비 기준(0.55) 아래다.
`FrontUpLeg_L`이 Spine 역할로 뽑힌 `Torso`의 자손이 아니라서 계층 점수 −0.18이 붙는다.
**매핑은 맞고 점수만 낮은 경우**이므로 등급이 과소평가다. 고치려면 "부모 역할의 자손은
아니지만 펠비스 아래에는 있다"를 따로 세는 게 맞고, 1,691개 감사에 영향이 가니 따로 잰다.

FK 체인 길이 비율 보간과 같은 모양이다. `UPT.FKOneToOne 1`로 35쌍을 다시 쟀다.

| 조합 | 최악 (기본) | 최악 (One to One) | 발 높이 오차 |

| Synty → Manny | 8.4° | **0.1°** | 0.0121 → 0.0252 |
| Synty → Forest Golem | 7.8° | **0.1°** | 0.0248 → 0.0511 |
| Synty → X_Bot | 7.1° | **0.1°** | 0.0222 → 0.0308 |

보간을 쓴다(발이 땅에 붙는 쪽이 쓸모가 크다). 드래곤의 목은 본이 6개 대 1개라 개수가
달라 1:1이 적용되지 않는다 — 8.6°는 그 구조 차이다.

`Wolf_Cub → Polygonal_Wolf`의 35.3°는 **1:1로도 소수 첫째 자리까지 그대로**였다. 즉 FK 보간이
원인이 아니다. 세 애니메이션 중 `Wolfr_Howl` 하나에서만 크고(Idle 2.8° / Bark 8.5° / Howl 27.7°),
움직임 성분은 5.2°뿐이라 **포즈에 따라 달라지는 상수 오프셋**이다. 레스트 포즈 회전 오프셋
하나로는 관절 축이 다른 리그를 보정할 수 없다는 쪽이 유력하지만, **아직 증명하지 않았다.**
수치를 이름으로 못 박아 두었으니 조용히 나빠지지는 않는다.

### 쇄골 체인 중복을 고쳐 봤지만 효과가 없어 되돌렸다

`LeftClavicle → LeftUpperArm` 체인은 위팔을 삼킨다. 위팔은 `LeftArm` 체인의 시작 본이기도
해서 **한 본이 두 체인에 동시에 들어간다** — 앞에서 Spine·Neck에 대해 고친 것과 똑같은
모양이고, 엔진 Auto Characterizer도 쇄골을 한 본으로 끊는다. 쇄골이 한쪽에만 있는 늑대 쌍에서
특히 아플 것으로 봤다.

같은 방식으로 줄여 35쌍을 다시 쟀다. **소수 둘째 자리까지 한 자리도 바뀌지 않았다.**
중복 소속은 사실이지만 결과에는 영향이 없다. 효과 없는 변경을 남기지 않기로 하고 되돌렸다
(IK 목표·바닥 제약·루트 고정과 같은 처리). 코드에는 측정 결과를 주석으로 남겼다.

### 새로 드러난 것: 골렘 손가락이 20°

`Polygonal_Golem`은 손가락이 있는 **세 번째** 대상이고, 손가락 마디 오차가 중앙 **20.2°**,
최악 43.9°다(Manny 0.0° / X_Bot 0.0°). 라벨 불일치는 아니다 — 손가락 본이 `RigLArmPalm →
RigLArmIndex1 → Index2 → Index3`의 정상 사슬이고 좌우 대칭이며, C++ 분석기와 파이썬 측정기가
같은 본을 가리킨다(부모 사슬을 찍어 확인했다). 정렬기도 33마디/33본을 처리했다고 찍는다.
움직임 성분은 1.3°뿐이라 **상수 오프셋**이다. 원인은 아직 모른다. 수치를 조합별로 못 박았다.

접지 지표(`foot_*` / `contact_mismatch`)는 각도와 독립이다. 펠비스 이동을 직접 구워 넣은 뒤 크게 조였다.

전체 지표와 조합별 지표를 **둘 다** 둔다. 조합별 기준만 있으면 한 조합이 좋아지고 다른
조합이 나빠지는 변화를 통과시킨다(접선 보간을 시도했을 때 실제로 그랬다 — UE4 팔은 절반,
표준 묶음은 13.3° → 18.1°). 거꾸로 전체 기준만 있으면 **어려운 조합을 하나 넣는 순간
전체 가드가 그 조합에 맞춰 느슨해지고 사람 쌍의 퇴행이 그 밑에 숨는다.** 사족·비인간 쌍을
넣을 때 발 높이 최악이 0.0413 → 0.0824로 뛴 것이 그 경우였다. 그래서 느슨해진 전체 기준
세 줄(`worst_segment_deg` / `foot_clearance_worst` / `finger_worst_deg`)은 **어느 쌍의 값인지
이름을 적어** 두고, 실제 조임은 조합별 기준이 담당한다.

`run_regression.py --only retarget`으로 돌린다.
전체 12개 스위트 모두 통과 상태다(비디오·자세 스위트는 `ThirdParty/UPTAnalyzer/.venv`의 파이썬으로 돌려야 한다).

## 남은 것

- 베이커는 **회전은 손대지 않는다.** 지금은 엔진 op이 동작하므로 쓰이지 않지만, 또 다른 비표준
  리그에서 베이커가 실제로 돌게 되면 회전 쪽이 빠진 영향을 재야 한다.
- 남은 최악 뼈마디는 세 대상 모두 `calf→foot` (7.1°~8.4°)다. **원인은 찾았다** — FK 체인의
  길이 비율 보간이다(위 절). 고치는 수단도 있지만(`UPT.FKOneToOne`) 접지를 대가로 내므로
  기본으로 켜지 않았다. 둘을 모두 얻으려면 `One to One`에 바닥 제약이나 접지 고정 op을
  붙여 재야 한다. **다음에 손댈 곳은 여기다.**
- 접지를 더 조일 방법이 남아 있지 않다. IK 쪽은 세 구성 모두 재 보고 기각했다(위 절).
  `One to One`이 각도를 0.1°까지 떨어뜨리지만 접지를 대가로 내는 것도 그대로다.
  다음에 시도한다면 접지 고정(`SpeedPlantingOp`)이거나, 각도·접지 중 무엇을 살릴지
  **에셋마다 고르게 하는 것**이다. 지금은 스위치로 둘 다 열어 두었다.
- 역할 그래프는 **손가락·발가락·트위스트 본을 다루지 않는다.** 지금 지표가 재는 범위 밖이라
  영향이 보이지 않지만, 손 자세를 재는 지표를 만들면 역할 목록을 늘려야 한다.

## 다시 돌리는 법

측정 한 벌(19쌍)을 한 번에 돌리는 진입점을 만들어 두었다. 조합 목록이 스크립트 안에 있으므로
조합을 빠뜨리거나 manifest를 섞어서 "쌍이 줄어든 채로 통과"하는 일이 없다.

```bash
"C:/Program Files/Epic Games/UE_5.7/Engine/Binaries/Win64/UnrealEditor.exe" <프로젝트>.uproject -ExecCmds="py <플러그인>/Tools/eval/editor/upt_run_retarget_suite.py, quit" -unattended -nosplash -nop4
```

그다음 베이스라인과 비교한다.

```bash
python Tools/eval/run_regression.py --only retarget
```

비교용 스위치는 그대로 있다. 둘 다 `-ExecCmds`의 앞에 끼워 넣으면 된다.

```
UPT.RestPoseAlign 0      # 레스트 포즈 정렬을 끈다
UPT.ForceFallbackRig 1   # 엔진 Characterize 대신 자체 분석 Rig을 쓴다
UPT.FKOneToOne 1         # 본 개수가 같은 체인의 FK 회전을 1:1로 (각도↑ 접지↓)
UPT.GenerateIKGoals 1    # IK Rig에 FBIK Goal과 Solver를 만든다 (기본 끔, 켜면 전반적으로 나빠진다)
UPT.FloorConstraint 1    # 다리 체인에 바닥 제약 op을 붙인다 (Goal이 있어야 효과가 있다)
UPT.IKPinRoot 0          # FBIK 루트를 엔진 기본값 Free로 (기본은 PinToInput)
UPT.DisableIKOps 1       # IK 관련 op을 모두 끈다 (진단)
UPT.BakePelvisMotion 2   # 펠비스 이동이 이미 있어도 덮어쓴다
```
