# 영상에서 몸 동작 뽑기 — 측정 결과와 결론 (2026-09-25)

MetaHumanBodyTracker 플러그인이 없어 5.8 바디 캡처가 막혀, 대안으로 **영상 → 3D 관절(RTMW3D) → 애니메이션**
경로를 검토했다. 굽기 전에 정확도를 먼저 쟀고, **깊이가 쓸 수 없는 수준이라 애니메이션 굽기는 진행하지 않았다.**

## 결론 한 줄

2D 관절 위치는 쓸 만하지만(몸 높이 대비 7.2%), **깊이(z)는 사실상 잡음**이라 3D 관절로 뼈 회전을 만들 근거가 없다.

## 측정 방법

정답은 에디터에서 직접 만든다. `Tools/eval/editor/upt_capture_body_truth.py`가
달리기(`A_MOD_GBL_Run_F_Neut`) 16프레임 + 걷기(`A_MOD_GBL_Walk_F_Neut`) 24프레임을 24fps로 찍고,
같은 순간의 뼈 22개 월드 좌표와 화면 투영 좌표를 남긴다.
평가는 `Tools/eval/eval_body_pose.py`가 그 영상을 RTMW3D로 분석해 정답과 비교한다.

## 결과 (bodypose_20260925_162906, 40프레임)

| 지표 | 값 | 읽는 법 |
|---|---|---|
| `frames_without_person` | 0 | 사람 검출은 전 프레임 성공 |
| `screen_error` | 0.0271 | 관절 화면 위치 오차, 프레임 대비 2.7% |
| `screen_error_body_pct` | 7.2 | 같은 오차를 몸 높이로 환산하면 7.2% |
| `depth_correlation` | 0.215 | 추정 깊이와 실제 깊이의 상관. 1이면 완전 일치 |
| `pose_error_cm` | 21.7 | 회전·크기를 맞춘 뒤 남는 관절 거리 |
| `pose_error_floor_cm` | 21.3 | **정답의 2D를 그대로 넣었을 때의 같은 값** |

`pose_error_cm`(21.7)과 `pose_error_floor_cm`(21.3)이 거의 같다. 완벽한 2D를 넣어도 21.3cm가 남는다는 뜻이므로,
이 21.7cm는 대부분 "3D 정답을 평면과 비교해서" 생기는 값이고 추정 깊이는 기여하지 않았다.
깊이 배율을 격자 탐색으로 최적화해도 21.7 → 21.3으로만 줄어 바닥값에 닿을 뿐이다.

깊이를 관절별로 따로 보면 더 분명하다.

| 관절 | 실제 깊이와의 상관 |
|---|---|
| hand_l | 0.47 |
| hand_r | **-0.35** (반대로 움직인다) |
| foot_l | 0.04 |
| foot_r | -0.04 |

어느 발이 앞에 나갔는지조차 구분하지 못한다.

## 그래서 멈춘 지점

계획의 3단계(관절 → 뼈 회전 → AnimSequence 굽기)는 **하지 않았다.** 깊이가 없으면 뼈 회전을 만들 수 없고,
2D만으로 만든 회전은 카메라를 정면에 고정한 경우에만 그럴듯해 보일 뿐 애니메이션으로 쓸 수 없다.

## 단서: 이 숫자의 한계

피사체가 사람이 아니라 투구·망토·검 두 자루를 든 저폴리 캐릭터다. RTMPose 계열은 사람 영상으로 학습했으므로
실제 사람 영상에서는 더 나을 수 있다. 다만 실제 사람 영상에는 3D 정답이 없어 같은 방식으로 검증할 수 없다.

## 다음에 시도할 만한 것

1. MetaHumanBodyTracker 플러그인 확보(Fab에서 계속 미확인). 확보되면 5.8 바디 캡처가 정공법이다.
2. 사람 피사체로 정답을 만들 방법(모션캡처 데이터가 있는 공개 데이터셋 + 그 데이터로 렌더한 영상).
3. 2D만 쓰는 용도로 한정: 구도·프레이밍 분석 보조(이미 쓰고 있는 pose-v8 경로)에는 지금 정확도로 충분하다.

## 에디터에서 자세를 갱신할 때 빠진 함정 (기록)

정답 촬영을 세 번 다시 만들었다. 원인은 모두 "에디터 월드에서는 애니메이션이 평가되지 않는다"였다.

1. `SkeletalMeshComponent.set_position()`만으로는 본 트랜스폼이 갱신되지 않는다. 40프레임이 전부
   레퍼런스 포즈로 굳었는데 이미지 차이가 0이 아니어서(안티앨리어싱 잡음) 처음엔 눈치채지 못했다.
2. `set_editor_property("animation_mode", ...)`는 애님 인스턴스를 다시 만들지 않는다. `set_animation_mode()`를 써야 한다.
3. `visibility_based_anim_tick_option`이 `ALWAYS_TICK_POSE`면 포즈는 틱해도 본 트랜스폼은 렌더될 때만 갱신된다.
4. 시퀀서에 애니메이션 트랙을 깔고 `set_current_time()`으로 스크럽해도 **섹션이 바뀔 때만** 자세가 바뀐다.
5. 결국 **시뮬레이트(PIE)를 켜서 월드가 실제로 틱하게** 해야 한다. 파이썬이 도는 동안에는 틱이 없으므로
   틱 콜백으로 '이번 틱에 자세 지정 → 다음 틱에 촬영' 순서로 진행한다.
6. 카메라(SceneCapture)는 `GameplayStatics`로 PIE 월드에 직접 스폰할 수 없다. 시뮬레이트 전에 에디터 월드에
   띄워 두면 복제되므로 이름으로 찾아 쓴다.
7. 역광이면 실루엣으로만 찍혀 포즈 추정이 실패한다. 카메라 쪽에 키 라이트(6만 루멘)를 둔다.

이 함정들 때문에 `upt_capture_body_truth.py`에는 **프레임마다 자세가 실제로 진행했는지** 확인하는 가드가 있다
(이웃 프레임 사이 손·발 이동 중앙값 0.5cm 미만이면 정답을 저장하지 않는다). 전체 이동 범위로 재면
클립이 바뀔 때 한 번 튄 것만으로 통과해 버려서, 반드시 연속 프레임 변화로 봐야 한다.
`eval_body_pose.py`에도 같은 취지의 가드가 있어 정지된 정답이면 평가를 건너뛴다.

## 회귀 검사

`Tools/eval/run_regression.py --only body_pose`로 돌린다. `baseline.json` 기준은 다음과 같다.

- `frames_without_person == 0`
- `screen_error <= 0.035`
- `screen_error_body_pct <= 9.0`

깊이는 지금 값(0.215)이 쓸 수 없는 수준이라 기준으로 걸지 않았다. 모델을 바꿔 깊이가 쓸 만해지면
그때 `depth_correlation`에 하한을 건다.
